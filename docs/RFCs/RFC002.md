## **1\. Introduction**

This document defines the **APTITUDE Presentation Profile** for interoperable credential verification across APTITUDE pilots.

It specifies a baseline, cross-pilot profile for presentation and verification of <credentials:Attestation|Attestations>. The mandatory `eu-eaap` profile is based on **OpenID for Verifiable Presentations (OpenID4VP) v1.0**, applies the applicable requirements of the **OpenID4VC High Assurance Interoperability Profile (HAIP) 1.0**, and further applies **ETSI TS 119 472-2** for the presentation protocol. Credential-format profiling for SD-JWT VC and ISO mdoc is taken from **ETSI TS 119 472-1**. ETSI TS 119 472-2 remains the presentation-protocol profile.

The optional `haip-vp`, `openid4vp`, and `mdoc-openid4vp` profiles do not inherit every HAIP or ETSI requirement defined here for `eu-eaap`. A requirement stated for `eu-eaap` applies to that profile only, unless this RFC explicitly extends it to another profile.

### **1.1 Reference baseline**

For D2.1, this RFC uses the following architectural and legal snapshot. Later ARF or CIR revisions are out of scope unless a subsequent RFC revision explicitly updates this baseline.

- **ARF v3.0.0** (2026-07-21) is the Architecture and Reference Framework reference. Subsequent mentions of “the ARF” in this RFC mean ARF v3.0.0.
- **CIR (EU) 2024/2982** (protocols and interfaces), as amended by **CIR (EU) 2026/1731**, is the presentation-protocol CIR. The applicable provisions are Article 3 (wallet-relying party authentication and validation), Article 5, and Annex II, which designate ETSI TS 119 472-2 V1.2.1 and ISO/IEC 18013-7:2025 Annex C for presentation of PID and electronic attestations of attributes.
- **CIR (EU) 2025/848** (registration of Wallet-Relying Parties), as amended by **CIR (EU) 2026/1730**, applies where this RFC transports or processes verifier registration material such as `verifier_info` and wallet-relying party registration certificates.
- **ETSI TS 119 472-1** profiles the SD-JWT VC and ISO mdoc credential formats used in a presentation. **ETSI TS 119 472-2** profiles the presentation protocol. This RFC does not use TS 119 472-1 as a second presentation-protocol profile.

In the remainder of this RFC, the short forms **CIR 2024/2982** and **CIR 2025/848** mean those acts as amended by CIR (EU) 2026/1731 and CIR (EU) 2026/1730 respectively. Generic “CIR” references without an identifier are not used.

The purpose of this RFC is to establish a stable starting point for interoperability across APTITUDE pilots by defining:

- common presentation and verification requirements  
- roles and interfaces between wallets and verifiers  
- baseline security and privacy expectations  
- support for same-device and cross-device presentation patterns  
- a requirements baseline that can be mapped into corresponding **ITB+ conformance test cases**

This RFC is intended to support interoperability first. Pilot-specific or sector-specific extensions may be added later, but they should not weaken the baseline requirements defined here.

## **2\. Scope**

This RFC defines the conformance profile for **credential presentation and verification** in APTITUDE.

It covers requirements for:

- **<components:Wallet Unit|Wallet Units> / Wallets** acting on behalf of the <roles:User>  
- **<roles:Relying Party (RP)|Relying Parties>** initiating presentation requests and validating responses, including a <roles:Relying Party (RP)|Relying Party> that operates through a <roles:Relying Party Intermediary (RPI)>

This profile defines a baseline for presentation interoperability using **OpenID4VP v1.0**.

Presentation profiles and credential formats are separate concerns. Except for `mdoc-openid4vp`, the presentation profiles defined by this RFC are credential-format agnostic and may be used with either SD-JWT VC (`dc+sd-jwt`) or ISO mdoc (`mso_mdoc`). Format-specific request, presentation, proof, and validation rules still apply for the selected credential format, as profiled by ETSI TS 119 472-1 where that specification applies to the format.

| Presentation profile | Requirement | Protocol profiling | Supported credential formats |
| --- | --- | --- | --- |
| `eu-eaap` | Mandatory | OpenID4VP, then HAIP, then ETSI TS 119 472-2 | `dc+sd-jwt`, `mso_mdoc` |
| `haip-vp` | Optional | OpenID4VP and HAIP, without the further ETSI TS 119 472-2 constraints of `eu-eaap` | `dc+sd-jwt`, `mso_mdoc` |
| `openid4vp` | Optional | OpenID4VP, without the HAIP and ETSI constraints of `eu-eaap` | `dc+sd-jwt`, `mso_mdoc` |
| `mdoc-openid4vp` | Optional | OpenID4VP remote mdoc profile in Section 5.6 | `mso_mdoc` only |

Support for a format-agnostic presentation profile does not by itself require an implementation to support every credential format. Conformance claims SHALL identify the credential format or formats supported under each claimed profile.

This RFC includes baseline requirements for:

- construction and processing of presentation requests
- Wallet invocation for same-device and cross-device presentation flows
- retrieval of a signed <artifacts:Request Object> for `eu-eaap`
- presentation response submission and verifier-side validation
- holder consent and release of requested data
- baseline privacy and security requirements for request/response handling

For the mandatory `eu-eaap` profile, the following requirements apply to both same-device and cross-device non-API-mediated flows:

- signed <artifacts:Request Object|Request Objects> passed by `request_uri`
- `client_id` using the Client Identifier Prefix `x509_hash`
- same-device invocation using the `eu-eaap://` scheme
- structured <roles:Relying Party (RP)|Relying Party> identification, including ETSI registrar information in `verifier_info`
- `response_type=vp_token`, `response_mode=direct_post.jwt`, and delivery to `response_uri`
- encrypted presentation responses using the algorithms in Section 8.4.2
- holder binding where the selected credential and request require it, including a KB-JWT for a holder-bound SD-JWT VC presentation

The same-device `redirect_uri` completion in Section 6.1.9 applies only to same-device `eu-eaap`. It does not apply to cross-device presentation.

For the optional `mdoc-openid4vp` profile, the following additional requirements apply:

- format-specific wallet invocation using the `mdoc-openid4vp://` scheme
- `mso_mdoc` request construction with document type, <data-elements:Namespace|namespace>, and element identifiers
- `vp_token` carrying the base64url-encoded ISO `DeviceResponse` CBOR structure
- `SessionTranscript` and handover construction binding the response to the originating request
- verifier-side validation of the returned mdoc presentation object against the reconstructed session context

This RFC does **not** define:

- sector-specific credential semantics  
- trust-path construction, List of Trusted Entities processing, Trust Anchor extraction, or certificate-status processing; RFC003 and RFC004 define those procedures
- full protocol profiling of ISO/IEC 18013-5 proximity device retrieval and reader authentication requirements
- JSON-LD W3C VC presentation requirements
- pilot-specific UI requirements  
- detailed test assertions; these are derived into the ITB+ test suite from the requirements matrix in this document
- a rule that every APTITUDE <roles:Relying Party (RP)|Relying Party> holds a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>

This RFC does require the presentation-time outcomes of RFC003 and RFC004. The Wallet and the <roles:Relying Party (RP)|Relying Party> SHALL obtain those outcomes before relying on a request or a returned credential. This RFC does not restate the procedures that produce them.

Where this RFC defines structural elements that may also be used by a trust framework or verifier registration ecosystem, those definitions support interoperability of the protocol exchange. They do not by themselves replace RFC003 or RFC004.

## **4\. Roles and Components**

This RFC uses the following roles:

### **4.1 User**

The **<roles:User>**, as defined in the APTITUDE glossary, is the natural person or legal representative controlling the Wallet and authorising the presentation of credentials.

### **4.2 Wallet Unit / Wallet**

The **Wallet Unit** is the <components:Wallet Unit> as defined in ARF v3.0.0 and the APTITUDE glossary, including one or more <components:Wallet Instance|Wallet Instances> on the Holder’s device or environment. In this RFC, the term **Wallet** refers to the Wallet Unit (and its Wallet Instances) when the distinction is not material, acting on behalf of the <roles:User> to manage credentials and respond to presentation requests.

### **4.3 Relying Party**

The **<roles:Relying Party (RP)|Relying Party>**, as defined in the APTITUDE glossary, is the entity requesting verifiable presentations, validating the response, and making an authorisation or business decision based on the outcome.

A <roles:Relying Party (RP)|Relying Party> may operate through a <roles:Relying Party Intermediary (RPI)> where the presentation flow uses an intermediary. The intermediary is the party authenticated for the protocol exchange. `verifier_info` identifies the final <roles:Relying Party (RP)|Relying Party> on whose behalf the attributes are requested. RFC003 defines the direct and intermediary binding rules.

### **4.4 Relying Party Backend**

The **<components:Verifier Backend|Relying Party Backend>**, as defined in the APTITUDE glossary, is the server-side component that creates presentation requests, receives presentation responses, validates them, and returns the result to the <components:Relying Party Instance>.

### **4.5 Relying Party Instance**

The **<components:Relying Party Instance>**, as defined in the APTITUDE glossary, is the software and/or hardware module in which credential verification is performed. It is controlled by a <roles:Relying Party (RP)|Relying Party>. The <components:Relying Party Instance> is not the <roles:Relying Party Intermediary (RPI)> role.

### **4.6 Relying Party Intermediary**

The **<roles:Relying Party Intermediary (RPI)>** is a <roles:Relying Party (RP)|Relying Party> that connects to a Wallet Unit on behalf of another <roles:Relying Party (RP)|Relying Party>. Where a presentation is intermediated, the intermediary is authenticated with the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> that signs the <artifacts:Request Object>. The final <roles:Relying Party (RP)|Relying Party> is identified by the registrar information in `verifier_info`. Authorization of that relationship is defined by RFC003.

## **5\. Protocol Overview**

The APTITUDE Presentation Profile uses **OpenID4VP v1.0** as the presentation protocol for requesting and submitting credential presentations.

The mandatory `eu-eaap` profile applies HAIP requirements and then the further requirements of ETSI TS 119 472-2. The optional `haip-vp` profile applies HAIP without those further ETSI presentation-protocol constraints. The optional `openid4vp` profile applies OpenID4VP without the HAIP and ETSI constraints of `eu-eaap`. The optional `mdoc-openid4vp` profile is specific to `mso_mdoc` and is defined in Section 5.6.

The mandatory `eu-eaap` profile and the optional `haip-vp` and `openid4vp` profiles are credential-format agnostic. Each may carry SD-JWT VC or mdoc presentations using the format-specific processing rules of ETSI TS 119 472-1, OpenID4VP, and the selected presentation profile. The optional `mdoc-openid4vp` profile is specific to `mso_mdoc`.

### **5.1 Common presentation sequence**

In the presentation flows in this RFC:

- the <roles:Relying Party (RP)|Relying Party> creates a <artifacts:Presentation Request> using OpenID4VP request parameters
- the Wallet is invoked using a same-device or cross-device mechanism
- the Wallet validates the request before showing it to the <roles:User>
- the <roles:User> reviews the request and explicitly approves release
- the Wallet generates a presentation response using the selected credential format
- the Wallet submits the response using the response mechanism of the selected profile
- the <roles:Relying Party (RP)|Relying Party> validates the response and returns the outcome to the <components:Relying Party Instance>

For `eu-eaap`, Section 5.2 replaces the general response mechanism, request protection, and invocation rules above.

Structural request elements used by a trust framework do not by themselves establish trust, legal reliance, or registration status. Trust and status outcomes required before reliance are those defined by RFC003 and RFC004.

### **5.2 `eu-eaap` mandatory requirements**

A presentation using the `eu-eaap` profile SHALL apply the following constraints in both the same-device flow and the cross-device flow. These constraints are properties of `eu-eaap`. They are not implied for `haip-vp`, `openid4vp`, or `mdoc-openid4vp`.

- The <artifacts:Presentation Request> SHALL be a signed JWT <artifacts:Request Object> as defined by RFC 9101, with JOSE header `typ` set to `oauth-authz-req+jwt`.
- The signed <artifacts:Request Object> SHALL be passed by reference. The Authorization Request SHALL contain `request_uri`. The <artifacts:Request Object> SHALL NOT be transported by value.
- `client_id` SHALL use the Client Identifier Prefix `x509_hash`. The Authorization Request `client_id` and the <artifacts:Request Object> `client_id` SHALL be identical, including the prefix.
- The <artifacts:Request Object> SHALL be signed with the private key corresponding to the leaf <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> carried in the `x5c` header.
- `verifier_info` SHALL contain the registrar information required by ETSI TS 119 472-2.
- `client_metadata` SHALL contain the ephemeral response-encryption key material defined in Section 8.4.2.
- The <artifacts:Request Object> SHALL contain `aud`, <data-elements:Nonce|`nonce`>, and `state`.
- `response_type` SHALL be `vp_token`. `response_mode` SHALL be `direct_post.jwt`. The Wallet SHALL send the encrypted response to `response_uri`.
- The Wallet SHALL encrypt the authorization response with ECDH-ES on curve P-256 and with `A128GCM` or `A256GCM`, as specified in Section 8.4.2.
- The Wallet SHALL use cryptographic holder binding where the selected credential and the request require it. For a holder-bound SD-JWT VC presentation, the Wallet SHALL include a KB-JWT.

The high-level sequence is independent of whether the Wallet retrieves the <artifacts:Request Object> with HTTP GET or HTTP POST. Section 8.2 defines both retrieval methods. POST is permitted and is not required.

These structures support interoperability of the protocol exchange. RFC003 and RFC004 define how trust evidence is validated. This RFC defines which of those outcomes the presentation flow requires.

### **5.3 Supported presentation patterns**

This RFC supports **non-API-mediated** presentation patterns:

- **same-device presentation**, where the Wallet is invoked on the same device as the <components:Relying Party Instance>; and
- **cross-device presentation**, where the request is transferred across devices, typically using QR-based or link-based handoff

For `eu-eaap`, `haip-vp`, and `openid4vp`, APTITUDE requires support for interoperable invocation methods suitable for same-device and cross-device non-API-mediated use, independently of whether the selected credential format is `dc+sd-jwt` or `mso_mdoc`.

For `eu-eaap` same-device presentation, the Wallet and the <roles:Relying Party (RP)|Relying Party> SHALL support invocation through the `eu-eaap://` scheme. Other URI schemes are not required for an `eu-eaap` conformance claim.

For the optional **`mdoc-openid4vp`** profile, same-device remote presentation is the ISO-aligned mode. Cross-device presentation under `mdoc-openid4vp` is not defined in this RFC. If APTITUDE requires it in future, it SHALL be described as a separate profile claim and SHALL NOT be presented as ISO/IEC 18013-7 alignment.

API-mediated presentation flows are currently out of scope for this RFC. Future revisions may include API-mediated flows (for example, DC API) where required by agreed use cases.

### **5.4 High-level presentation sequence**

At a high level, the `eu-eaap` presentation process is:

1. The <roles:Relying Party (RP)|Relying Party> optionally retrieves Wallet Metadata when the Wallet’s capabilities are not already known or configured.
2. The <roles:Relying Party (RP)|Relying Party> creates a signed <artifacts:Presentation Request>.
3. The Wallet is invoked with the Authorization Request parameters, including `client_id`, `request_uri`, and `request_uri_method` when that parameter is used.
4. The Wallet retrieves the signed <artifacts:Request Object> from `request_uri`.
5. The Wallet validates the <artifacts:Request Object>, including the trust outcomes required by Section 6.1.5.
6. The <roles:User> reviews the request, including `transaction_data` when the request contains it, and provides consent.
7. The Wallet generates the presentation and encrypts the authorization response.
8. The Wallet submits the encrypted response to `response_uri` using `direct_post.jwt`.
9. For same-device presentation only, the Wallet follows the `redirect_uri` returned by the <roles:Relying Party (RP)|Relying Party>, and the <roles:Relying Party (RP)|Relying Party> correlates that return with the originating browser session.
10. The <roles:Relying Party (RP)|Relying Party> decrypts the response, correlates it to the transaction, validates the presentation, obtains the credential trust and status outcomes required by Section 7.2, and returns the outcome.

Steps 1 and 9 are the only steps that are optional or flow-specific. Step 1 is omitted when Wallet capabilities are already known or configured. Step 9 does not apply to cross-device presentation. Steps 2 to 8 and step 10 apply to both flows. The sequence does not depend on GET versus POST retrieval.

### **5.5 Relation to ETSI presentation and credential-format profiling**

ETSI TS 119 472-1 defines general requirements and credential-format profiling, including SD-JWT VC and ISO mdoc. This RFC uses TS 119 472-1 for those format rules. It does not use TS 119 472-1 to select the presentation protocol.

ETSI TS 119 472-2 separates:

- an **ISO/IEC-mdoc profile** (clause 5) for proximity-based non-API-mediated device retrieval built on ISO/IEC 18013-5, and
- an **OpenID4VC-HAIP-based profile** (clause 6) for API-mediated and non-API-mediated transmission.

The `eu-eaap` profile in this RFC corresponds to the non-API-mediated application of ETSI TS 119 472-2 clause 6. OpenID4VP 1.0 and HAIP 1.0 define presentation processing for both SD-JWT VC and mdoc. This RFC does not create separate `eu-eaap`, `haip-vp`, or `openid4vp` presentation profiles per credential format. The selected credential format determines the applicable format-specific request, proof, presentation-object, and validation rules.

The `mdoc-openid4vp` profile remains separate because its invocation and session-binding behavior is specific to ISO mdoc. It is not required merely because an `mso_mdoc` credential is presented under `eu-eaap`, `haip-vp`, or `openid4vp`.

This RFC does **not** reproduce the ETSI clause 5 ISO/IEC-mdoc proximity profile, since full ISO/IEC 18013-5 proximity device retrieval profiling is out of scope here. This RFC also currently specifies only non-API-mediated presentation mechanisms. API-mediated mechanisms are not specified in this version and may be added in future revisions if required by use cases. For clarity, ETSI clause 5 proximity presentation uses the `RequestInfo` parameter to transport verifier registration certificate material or registrar information to the Wallet. This RFC acknowledges that ETSI mechanism, but does not normatively profile `RequestInfo` processing in this version because the full ISO/IEC 18013-5 proximity flow is out of scope.

### **5.6 `mdoc-openid4vp` profile**

This RFC defines the optional `mdoc-openid4vp` profile for remote presentation of `mso_mdoc` credentials over OpenID4VP.

**Accuracy note on protocol lineage.**
ISO/IEC TS 18013-7 Annex B references an earlier OpenID4VP draft. This RFC uses OpenID4VP v1.0 as its normative protocol baseline and does not introduce a dependency on that legacy draft.

Under this profile:

- the Wallet is invoked using the `mdoc-openid4vp://` scheme for same-device remote presentation
- the <artifacts:Presentation Request> uses `format = mso_mdoc` and identifies the requested document type, <data-elements:Namespace|namespaces>, and data elements compatible with ISO mdoc processing
- the <artifacts:Presentation Request> is obtained using `request_uri`
- the <artifacts:Presentation Request> includes the <data-elements:Nonce|nonce> and verifier identity inputs needed to construct the ISO-linked `SessionTranscript`
- the Wallet constructs the `SessionTranscript` using the OpenID4VP-to-ISO handover mapping defined for remote mdoc presentation
- the `vp_token` carries the base64url-encoded ISO `DeviceResponse` CBOR structure
- the Wallet binds the returned `DeviceResponse` to the originating request through the `SessionTranscript`
- the <roles:Relying Party (RP)|Relying Party> reconstructs and validates the same `SessionTranscript` inputs when validating the returned mdoc presentation
- the <roles:Relying Party (RP)|Relying Party> performs ISO-bound validation of the `DeviceResponse`, including document type match, <data-elements:Namespace|namespace> and element consistency, <data-elements:Nonce|nonce> and handover consistency, and cryptographic validation against the reconstructed session context
- encrypted response protection is applied using an encrypted response mode supported by the selected OpenID4VP mdoc profile

This profile is distinct from presenting `mso_mdoc` under the format-agnostic `eu-eaap`, `haip-vp`, or `openid4vp` profiles. Implementations claiming `mdoc-openid4vp` SHALL conform to the additional requirements defined for this profile. An `mdoc-openid4vp` claim does not by itself include the `eu-eaap` requirements in Section 5.2. The encryption algorithms in Section 8.4.2 are mandatory for `eu-eaap` and are not imported into `mdoc-openid4vp` by this RFC.

## **6\. High-Level Flows**

The step order in this section is the common presentation pattern. Normative statements that name `eu-eaap` apply to that profile in both the same-device flow and the cross-device flow, except for Section 6.1.9. Section 6.1.9 applies only to same-device `eu-eaap`.

The optional `haip-vp`, `openid4vp`, and `mdoc-openid4vp` profiles follow the invocation, consent, and submission pattern of this section using the rules of those profiles. They do not inherit the `eu-eaap` constraints unless a requirement in this RFC says that they do.

### **6.1 Same-Device Presentation Flow**

#### **6.1.1 Wallet Metadata discovery**

Before creating a <artifacts:Presentation Request>, the <roles:Relying Party (RP)|Relying Party> MAY retrieve the Wallet’s metadata as defined in Section 8.5.

The <roles:Relying Party (RP)|Relying Party> MAY omit this step when the Wallet’s presentation capabilities are already known or configured. Metadata retrieval is not a precondition for a single `eu-eaap` transaction.

This step is distinct from `request_uri_method=post`. POST retrieval, when used, is defined in Section 8.2.

#### **6.1.2 Presentation Request Creation**

The <roles:Relying Party (RP)|Relying Party> prepares a <artifacts:Presentation Request> containing the information needed by the Wallet to determine what credentials and claims are requested, along with the parameters needed to produce a valid response.

For `eu-eaap`, the <artifacts:Presentation Request> SHALL be a signed <artifacts:Request Object>. It SHALL include:

- `client_id` with the Client Identifier Prefix `x509_hash`
- `aud`
- <data-elements:Nonce|`nonce`>
- `state`
- `response_type=vp_token`
- `response_mode=direct_post.jwt`
- `response_uri`
- `client_metadata` containing the ephemeral encryption key material required by Section 8.4.2
- `dcql_query`
- `verifier_info` containing the ETSI registrar information required by Section 8.3.2
- validity and expiry parameters

For `eu-eaap`, the signed <artifacts:Request Object> SHALL NOT be placed in the Authorization Request. The Authorization Request passes it by `request_uri`.

#### **6.1.3 Wallet Invocation**

For `eu-eaap`, the <roles:Relying Party (RP)|Relying Party> SHALL invoke the Wallet with an Authorization Request that contains:

- `client_id`, using the Client Identifier Prefix `x509_hash`
- `request_uri`
- `request_uri_method`, when the retrieval method is not the default HTTP GET
- the `eu-eaap://` URI scheme

The Authorization Request SHALL NOT contain the signed <artifacts:Request Object> by value.

The `client_id` in the Authorization Request SHALL be identical to the `client_id` in the signed <artifacts:Request Object>, including the `x509_hash` prefix.

For the optional **`mdoc-openid4vp`** profile, same-device wallet invocation SHALL use the `mdoc-openid4vp://` scheme as required by Section 5.6. That requirement does not change `eu-eaap` invocation.

#### **6.1.4 Request Object Retrieval**

After invocation, and before request validation, the Wallet SHALL retrieve the signed <artifacts:Request Object> from `request_uri`, as defined in Section 8.2.

The Wallet SHALL treat the retrieved object as the presentation request. The Wallet SHALL use the parameters inside that object. The retrieval step applies whether the Authorization Request selects HTTP GET or HTTP POST. The sequence in this section does not otherwise depend on that choice.

#### **6.1.5 Wallet Validation**

The Wallet SHALL validate the retrieved <artifacts:Presentation Request> before presenting it to the <roles:User>.

For `eu-eaap`, validation SHALL include:

- request syntax and completeness
- the <artifacts:Request Object> signature and `typ`
- <data-elements:Nonce|nonce> presence and freshness
- audience binding
- expiry validity
- `response_type`, `response_mode`, and `response_uri`
- `dcql_query` semantics and compatibility with the Wallet’s supported credential formats
- presence of the `client_metadata` encryption key material required by Section 8.4.2
- presence of the registrar information in `verifier_info`

Signature validation is mandatory for `eu-eaap`. The Wallet verifies the signature with the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> in the `x5c` header. The `client_metadata` key material is the response-encryption key. It is not the request-verification key.

Before consent, the Wallet SHALL obtain the following trust outcomes. RFC003 and RFC004 define the procedures. This RFC requires the outcomes and does not restate path validation, List of Trusted Entities processing, Trust Anchor extraction, or status processing.

- Authentication of the requesting party SHALL succeed under RFC003, using the <artifacts:Request Object> signature and the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>, including the status outcome required by RFC004.
- The Wallet SHALL process the registrar information in `verifier_info` as the verifier context for the final <roles:Relying Party (RP)|Relying Party>.
- Where the applicable registration or trust profile requires a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>, the Wallet SHALL validate that certificate under RFC003 and RFC004. If that profile requires a WRPRC and the certificate is missing or invalid, authorization fails under RFC003.

Invalid, unsigned, expired, or otherwise malformed requests SHALL be rejected.

#### **6.1.6 Holder Consent**

The Wallet SHALL present the request information to the <roles:User> in a transparent way before generating a presentation.

For `eu-eaap`, the Wallet SHALL display:

- the final <roles:Relying Party (RP)|Relying Party> identity taken from the registrar information
- the purpose or context of the request
- the requested credential(s)
- the requested claims or attributes
- selective disclosure details for the approved release
- `transaction_data`, when the <artifacts:Request Object> contains it

The <roles:User> SHALL explicitly approve the release before a presentation is generated. The Wallet SHALL NOT generate a successful `vp_token` before that approval.

#### **6.1.7 Presentation Generation**

The Wallet generates a presentation only after the consent in Section 6.1.6.

For `eu-eaap`, a successful presentation SHALL include a `vp_token` that satisfies `dcql_query`, and the Wallet SHALL then encrypt the authorization response as required by Section 8.4.2.

Holder binding SHALL be used where the selected credential and the request require it. OpenID4VP `require_cryptographic_holder_binding` defaults to required. A presentation without holder binding is permitted only when the request explicitly allows it for that credential. <data-elements:Nonce|Nonce>, `state`, `aud`, and browser-session correlation do not replace cryptographic holder binding.

For a holder-bound **SD-JWT VC** presentation, the Wallet SHALL generate a KB-JWT as defined by RFC 9901 and OpenID4VP. The KB-JWT SHALL cover:

- a valid holder-binding signature
- `aud` bound to the <roles:Relying Party (RP)|Relying Party> `client_id`
- the request <data-elements:Nonce|`nonce`>
- `sd_hash` over the presented SD-JWT and disclosures
- `transaction_data_hashes` for each `transaction_data` value in the request, using the hash algorithm required by the request

When the request contains `transaction_data`, the Wallet SHALL generate those hashes only for the transaction data shown to the <roles:User> for that same <roles:Relying Party (RP)|Relying Party> transaction.

For an **SD-JWT VC** presentation that the request explicitly allows without holder binding, the Wallet SHALL omit the KB-JWT and SHALL still preserve request and response correlation.

For `mso_mdoc` presented under `eu-eaap`, the Wallet SHALL apply the mdoc proof rules of OpenID4VP, HAIP, and ETSI TS 119 472-1. Those rules are separate from the `mdoc-openid4vp` `SessionTranscript` requirements, which apply only when that optional profile is claimed.

For the optional **`mdoc-openid4vp`** profile, the Wallet SHALL:

- construct the `SessionTranscript` using the OpenID4VP-to-ISO handover mapping defined for remote mdoc presentation
- generate an ISO `DeviceResponse` CBOR structure bound to the originating request through the `SessionTranscript`
- encode the `DeviceResponse` as a base64url string and place it in the `vp_token`

#### **6.1.8 Presentation Submission**

For `eu-eaap`, the Wallet SHALL POST the encrypted authorization response to the <components:Verifier Backend|Relying Party Backend> at `response_uri`, using `response_mode=direct_post.jwt`.

The encrypted response SHALL NOT be returned through the browser or another front channel. The browser is used for Wallet invocation and, after submission, for the redirect in Section 6.1.9.

#### **6.1.9 Same-device redirect and session completion**

This step applies only to same-device `eu-eaap`. It does not apply to cross-device presentation.

After the Wallet POSTs the encrypted response to `response_uri`, the <roles:Relying Party (RP)|Relying Party> returns a `redirect_uri` as defined by OpenID4VP and HAIP. The Wallet SHALL follow that `redirect_uri` in the same-device session.

The <roles:Relying Party (RP)|Relying Party> SHALL correlate the return navigation with the browser session that started the transaction. The <roles:Relying Party (RP)|Relying Party> SHALL reject a missing return or a return associated with a different session.

This correlation binds the browser session to the transaction. It is not holder binding and it does not satisfy Section 6.1.7.

#### **6.1.10 Result Handling**

For `eu-eaap`, the <roles:Relying Party (RP)|Relying Party> SHALL:

1. receive the encrypted response at `response_uri`
2. decrypt the response with the private key corresponding to the ephemeral key in `client_metadata`
3. correlate the decrypted response to the originating transaction, including `state` and the same-device redirect correlation in Section 6.1.9
4. validate the presentation as required by Section 7.2
5. return the outcome

The outcome SHOULD clearly indicate:

- successful verification  
- verification failure  
- user cancellation  
- unsupported request or unsupported credential format  
- expired or invalid request  
- other protocol or validation errors

The Wallet and/or <components:Relying Party Instance> SHOULD display an understandable outcome to the <roles:User>. The <roles:Relying Party (RP)|Relying Party> continues the service only after successful presentation processing and successful same-device redirect completion.

### **6.2 Cross-Device Presentation Flow (Non-API-mediated)**

Cross-device presentation as defined in this section applies to `eu-eaap`, `haip-vp`, and `openid4vp`, for either supported credential format. The optional `mdoc-openid4vp` profile does not define cross-device presentation under this RFC. If cross-device `mdoc-openid4vp` presentation is required in future, it SHALL be described as a separate profile claim.

The `eu-eaap` rules in this section are the same rules as in Section 6.1, except that Section 6.1.9 does not apply. The cross-device flow has no `redirect_uri` session-completion step.

#### **6.2.1 Wallet Metadata discovery**

Section 6.1.1 applies. The <roles:Relying Party (RP)|Relying Party> MAY retrieve Wallet Metadata before creating the request and MAY omit retrieval when the Wallet’s capabilities are already known or configured.

#### **6.2.2 Presentation Request Creation and Display**

Section 6.1.2 applies.

For `eu-eaap`, the <roles:Relying Party (RP)|Relying Party> creates a signed <artifacts:Request Object> and makes the Authorization Request available through a non-API-mediated cross-device transfer, typically by encoding `client_id`, `request_uri`, and `request_uri_method` when used, in a QR code or equivalent link. The signed <artifacts:Request Object> SHALL NOT be encoded by value in that transfer.

#### **6.2.3 Wallet Invocation via QR, Link, or Equivalent**

The <roles:User> uses a second device to invoke the Wallet with the Authorization Request.

For `eu-eaap`, the transferred Authorization Request SHALL contain `client_id` with the `x509_hash` prefix and `request_uri`. It SHALL contain `request_uri_method` when the retrieval method is not HTTP GET. It SHALL NOT contain the signed <artifacts:Request Object> by value.

APTITUDE requires support for cross-device presentation through non-API-mediated interoperable means such as:

- QR-based transfer  
- link-based transfer  
- other supported wallet invocation methods

This section does not define API-mediated cross-device presentation. API-mediated approaches (for example, DC API-based flows) may be specified in future RFC revisions where required by agreed use cases.

#### **6.2.4 Request Object Retrieval**

Section 6.1.4 applies. The Wallet SHALL retrieve the signed <artifacts:Request Object> from `request_uri` before validating it. GET and POST retrieval both use Section 8.2. The cross-device sequence does not otherwise depend on that choice.

#### **6.2.5 Wallet Validation**

Section 6.1.5 applies, including mandatory signature validation, registrar information, encryption-key material, and the RFC003 and RFC004 trust outcomes.

#### **6.2.6 Holder Consent**

Section 6.1.6 applies, including display of `transaction_data` when the request contains it, and explicit approval before a `vp_token` is generated.

#### **6.2.7 Presentation Generation**

Section 6.1.7 applies, including encryption of the authorization response, holder binding, the SD-JWT KB-JWT, and `transaction_data_hashes`.

#### **6.2.8 Presentation Submission**

Section 6.1.8 applies. The Wallet SHALL POST the encrypted authorization response to `response_uri` using `direct_post.jwt`. The response SHALL NOT travel through the browser on the device that displayed the QR code or link.

#### **6.2.9 Result Handling**

The <roles:Relying Party (RP)|Relying Party> SHALL receive the encrypted response, decrypt it, correlate it to the originating cross-device transaction, validate the presentation as required by Section 7.2, and return the outcome.

The cross-device flow does not use the `redirect_uri` completion in Section 6.1.9. Correlation uses the direct response, `state`, and the transaction that issued the Authorization Request. That correlation is not holder binding.

**APT-PRES-WALLET-EAAP-07**

**APT-PRES-WALLET-MDOC-03**  
Construct the `SessionTranscript` using the OpenID4VP-to-ISO handover mapping defined for remote mdoc presentation.

**APT-PRES-WALLET-MDOC-04**  
Generate an ISO `DeviceResponse` CBOR structure in response to a valid `mso_mdoc` <artifacts:Presentation Request>.

**APT-PRES-WALLET-MDOC-05**  
Bind the returned `DeviceResponse` to the originating request through the `SessionTranscript`.

**APT-PRES-WALLET-MDOC-06**  
Encode the `DeviceResponse` as a base64url string and place it in the `vp_token`.

**APT-PRES-WALLET-MDOC-07**

## **8\. Interface Definitions**

For `eu-eaap`, the following artefacts are distinct. The Wallet SHALL NOT treat one as a substitute for another.

| Artefact | Where it appears | Role in `eu-eaap` |
| --- | --- | --- |
| Authorization Request | Wallet invocation: `eu-eaap://` or the cross-device QR or link | Carries `client_id`, `request_uri`, and `request_uri_method` when used. Does not carry the signed <artifacts:Request Object> by value. |
| Signed <artifacts:Request Object> | Retrieved from `request_uri` | The integrity-protected presentation request. Contains `client_metadata`, `verifier_info`, `dcql_query`, and the response parameters. |
| Wallet Metadata | Optional RFC 8414 document published by the Wallet | Lets the <roles:Relying Party (RP)|Relying Party> learn Wallet capabilities before creating a request. Omitted when those capabilities are already known. |
| `client_metadata` | Inside the signed <artifacts:Request Object> | Carries the ephemeral response-encryption key. This is the verifier metadata used for the presentation exchange. |
| Verifier metadata endpoint | Optional deployment-specific publication | Not required for `eu-eaap`. See Section 8.6. |

### **8.1 Wallet Invocation Interface**

**Direction:** <roles:Relying Party (RP)|Relying Party> → Wallet  
**Purpose:** Invoke a Wallet for presentation with an Authorization Request

For `eu-eaap` same-device presentation, invocation SHALL use the `eu-eaap://` scheme. The Authorization Request SHALL include `client_id` and `request_uri`. It SHALL include `request_uri_method` when the value is not the default `get`. The `client_id` SHALL use the prefix `x509_hash`. The value after the prefix SHALL be the base64url-encoded SHA-256 hash of the DER-encoded leaf certificate, as defined by OpenID4VP.

For `eu-eaap` cross-device presentation, the same Authorization Request parameters SHALL be carried in the QR code or link. The custom scheme `eu-eaap://` is the same-device invocation mechanism. The cross-device transfer still carries `client_id` and `request_uri`.

For the optional `haip-vp` and `openid4vp` profiles, implementations SHALL support interoperable invocation methods appropriate to the claimed profile. Those profiles do not require `eu-eaap://` or `x509_hash` unless they incorporate those rules themselves.

Supported invocation methods for optional profiles MAY include:

- QR codes  
- HTTPS links  
- deep links  
- custom URI schemes  
- platform wallet invocation methods

For the optional **`mdoc-openid4vp`** profile, wallet invocation SHALL use the `mdoc-openid4vp://` scheme. Use of `mso_mdoc` under another presentation profile does not by itself require this scheme.

---

### **8.2 Signed Presentation Request Object Retrieval**

**Direction:** Wallet → <roles:Relying Party (RP)|Relying Party> `request_uri`  
**Purpose:** Retrieve the signed <artifacts:Request Object> after Wallet invocation

For `eu-eaap`, the Wallet SHALL call `request_uri` and SHALL process the signed <artifacts:Request Object> returned there. The high-level flows in Section 6 remain the same for GET and POST. This section defines the two methods.

The response to a successful retrieval SHALL be the signed JWT <artifacts:Request Object> with content type `application/oauth-authz-req+jwt`.

#### **8.2.1 HTTP GET**

When `request_uri_method` is absent or `get`, the Wallet SHALL retrieve the <artifacts:Request Object> with HTTP GET, as defined by RFC 9101.

HTTP GET is sufficient for `eu-eaap` conformance. A Wallet is not required to support POST.

#### **8.2.2 HTTP POST**

When `request_uri_method` is `post`, a Wallet that supports POST SHALL send HTTP POST to `request_uri` with content type `application/x-www-form-urlencoded` and `Accept: application/oauth-authz-req+jwt`, as defined by OpenID4VP.

The POST body MAY contain:

- `wallet_metadata`, a JSON object using the Wallet Metadata parameters in Section 8.5
- `wallet_nonce`, a fresh Wallet-generated nonce

If the Wallet sends `wallet_nonce`, the signed <artifacts:Request Object> SHALL contain the same value in the `wallet_nonce` claim. The Wallet SHALL reject a <artifacts:Request Object> that does not repeat that value.

POST lets the Wallet supply its capabilities at retrieval time. It is separate from the optional pre-request read in Section 8.5. A <roles:Relying Party (RP)|Relying Party> that already knows the Wallet’s capabilities MAY use GET and MAY omit both the pre-request read and POST.

`request_uri_method` SHALL NOT be present unless `request_uri` is present. This RFC does not require POST for `eu-eaap`.

A Wallet that does not support POST and receives `request_uri_method=post` SHALL retrieve the <artifacts:Request Object> with GET, as permitted by OpenID4VP, unless a later APTITUDE profile requires POST.

---

### **8.3 Presentation Request Object**

The signed <artifacts:Request Object> is the presentation request for `eu-eaap`. The Wallet SHALL NOT reconstruct required request parameters from Wallet Metadata or from an independently published verifier-metadata document when those parameters are required to be inside the <artifacts:Request Object>.

#### **8.3.1 Parameters**

For `eu-eaap`, the signed <artifacts:Request Object> SHALL include:

- `client_id`, using `x509_hash`, identical to the Authorization Request `client_id`
- `aud`
- <data-elements:Nonce|`nonce`>
- `state`
- `response_type` with the value `vp_token`
- `response_mode` with the value `direct_post.jwt`
- `response_uri`
- `client_metadata`, including the ephemeral encryption key
- `dcql_query`
- `verifier_info`, including ETSI registrar information
- expiry or equivalent request validity constraints

The JOSE header SHALL set `typ` to `oauth-authz-req+jwt` and SHALL carry the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> chain in `x5c`. The leaf certificate SHALL be the certificate whose SHA-256 hash is the `x509_hash` client identifier. The <artifacts:Request Object> SHALL be signed with the corresponding private key.

When retrieval used POST and the Wallet supplied `wallet_nonce`, the <artifacts:Request Object> SHALL include that `wallet_nonce`.

`transaction_data` SHALL be included when the transaction requires the <roles:User> to approve transaction-specific data, including the payment use cases that depend on it. It is not required in every `eu-eaap` request.

#### **8.3.2 Registrar information and registration certificates**

`verifier_info` SHALL carry the registrar information required by ETSI TS 119 472-2. That information is the registered context the Wallet presents to the <roles:User> and the context RFC003 uses to identify the final <roles:Relying Party (RP)|Relying Party>. It includes, as profiled by ETSI TS 119 472-2:

- the registered <roles:Relying Party (RP)|Relying Party> identifier
- the registrar
- the service description
- the intended use
- the purpose
- the privacy-policy reference

A <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC> is a different object from that registrar information. This RFC does not require every APTITUDE <roles:Relying Party (RP)|Relying Party> to hold a WRPRC. ETSI TS 119 472-2, as applied here, requires the registrar information above. It is not applied here as a requirement that every <roles:Relying Party (RP)|Relying Party> hold a WRPRC.

Where the applicable registration or trust profile requires a WRPRC, the <artifacts:Request Object> SHALL carry that certificate in `verifier_info`, and the Wallet SHALL validate it under RFC003 and RFC004. If that profile requires a WRPRC and the certificate is missing or invalid, authorization fails under RFC003. If APTITUDE later requires a WRPRC for every <roles:Relying Party (RP)|Relying Party>, that decision SHALL be stated as an APTITUDE policy requirement.

The Wallet presents the registrar information to the <roles:User>. Validation of the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>, and of the <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC> when the registration or trust profile requires one, uses RFC003 and RFC004. This RFC does not define a second set of path, trust-anchor, or status rules.

#### **8.3.3 Credential-format considerations**

For **SD-JWT VC** requests, the <artifacts:Presentation Request> SHALL identify the requested credential type and requested disclosures or constraints through `dcql_query`, consistent with OpenID4VP and ETSI TS 119 472-1.

For `mso_mdoc` requests under `eu-eaap` or `haip-vp`, the <artifacts:Presentation Request> SHALL use the mdoc credential-format parameters and processing rules defined by OpenID4VP v1.0, ETSI TS 119 472-1, and the selected presentation profile.

For `mso_mdoc` requests under the optional `openid4vp` profile, the <artifacts:Presentation Request> SHALL use the mdoc credential-format parameters of OpenID4VP v1.0.

#### **8.3.3.1 `mdoc-openid4vp` request requirements**

For the optional **`mdoc-openid4vp`** profile, the <artifacts:Presentation Request> SHALL:

- use `format = mso_mdoc`
- identify the requested document type
- identify requested data elements using <data-elements:Namespace|namespace> and element identifiers compatible with ISO mdoc processing
- be obtained using `request_uri` for the ISO-aligned remote flow
- include the <data-elements:Nonce|nonce> and verifier identity inputs needed to construct the ISO-linked `SessionTranscript`
- include in `verifier_info`, where the `mdoc-openid4vp` deployment profile requires it, verifier registration certificate material or registrar information needed by the Wallet

The <artifacts:Presentation Request> for remote mdoc presentation SHALL use the DCQL query mechanism with the ISO mdoc credential format specific parameters as defined by OpenID4VP.

#### **8.3.4 Request validation expectations**

The Wallet SHALL reject a <artifacts:Presentation Request> that is malformed, expired, missing required anti-replay inputs, or inconsistent with the selected profile.

For `eu-eaap`, the Wallet SHALL validate the signature of the <artifacts:Request Object> before relying on its contents. The Wallet SHALL validate `typ`, `client_id`, `aud`, <data-elements:Nonce|nonce>, expiry, and the `x5c` certificate restrictions of HAIP and ETSI TS 119 472-2 that apply to `x509_hash`. Certificate-path and status validation produce the RFC003 and RFC004 outcomes required by Section 6.1.5.

#### **8.3.5 `mdoc-openid4vp` session binding**

For the optional **`mdoc-openid4vp`** profile, this RFC defines the following normative session-binding requirements:

- the Wallet SHALL construct the `SessionTranscript` using the OpenID4VP-to-ISO handover mapping defined for remote mdoc presentation
- the Wallet SHALL bind the returned `DeviceResponse` to the originating request through the `SessionTranscript`
- the <roles:Relying Party (RP)|Relying Party> SHALL reconstruct and validate the same `SessionTranscript` inputs when validating the returned mdoc presentation

The `SessionTranscript` provides the core ISO security binding for remote mdoc presentation under this optional profile. Without correct construction and validation of the `SessionTranscript`, the presentation cannot be considered bound to the originating request and the <roles:Relying Party (RP)|Relying Party> session context.

### **8.4 Presentation Response Interface**

**Direction:** Wallet → <roles:Relying Party (RP)|Relying Party> `response_uri`  
**Method:** For `eu-eaap`, HTTP POST using `response_mode=direct_post.jwt`

For `eu-eaap`, the on-the-wire authorization response SHALL be an encrypted JWE in the `response` parameter, POSTed by the Wallet to `response_uri`. The browser SHALL NOT carry that response.

The decrypted payload SHALL contain the `vp_token` and the correlation values required to bind the response to the transaction, including `state`.

#### **8.4.1 Response contents**

For `eu-eaap`, the decrypted authorization response SHALL contain:

- `vp_token`
- `state`

It contains disclosures and holder-binding material inside the credential format carried by `vp_token`. For a holder-bound SD-JWT VC, that material includes the KB-JWT required by Section 6.1.7.

The Wallet SHALL return only the credential-derived data, disclosures, and proof material necessary to satisfy the approved request.

Wallet error responses for `eu-eaap` SHALL use the same `direct_post.jwt` submission to `response_uri`.

#### **8.4.2 `eu-eaap` response encryption**

For `eu-eaap`, response encryption is mandatory. The following rules apply:

- `response_mode` SHALL be `direct_post.jwt`
- the Wallet SHALL encrypt the response as a JWE
- the key-agreement algorithm SHALL be ECDH-ES
- the encryption key SHALL be an ephemeral EC key on curve P-256, generated by the <roles:Relying Party (RP)|Relying Party> for that request
- the Wallet SHALL support content encryption `A128GCM` and `A256GCM`
- the <roles:Relying Party (RP)|Relying Party> SHALL place the ephemeral public key, including `kid`, in `client_metadata` inside the signed <artifacts:Request Object>
- the <roles:Relying Party (RP)|Relying Party> SHALL decrypt the response with the corresponding private key before validating the presentation

The ephemeral `client_metadata` key encrypts the response. Request-object verification uses the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> in `x5c`.

For the optional **`mdoc-openid4vp`** profile, the following additional response-protection rules apply, without importing the `eu-eaap` algorithm set:

- the ISO-aligned mdoc profile SHALL use an encrypted response mode supported by the selected OpenID4VP mdoc profile
- the <roles:Relying Party (RP)|Relying Party> SHALL provide the parameters needed for the Wallet to protect the response accordingly
- the encrypted response SHALL carry the `DeviceResponse` as defined in Section 8.4.3.1

This RFC does **not** define trust-framework legal or supervisory effects of successful verifier authentication. Those effects, where they exist, are outside the protocol exchange.

#### **8.4.3 Credential-format considerations**

For **SD-JWT VC** presentation under `eu-eaap`, the `vp_token` SHALL contain the credential-derived presentation, only the disclosures necessary to satisfy the approved request, and the KB-JWT when holder binding is required.

For `mso_mdoc` presentation under `eu-eaap` or `haip-vp`, the response SHALL follow the mdoc credential-format processing rules of OpenID4VP v1.0, ETSI TS 119 472-1, and the selected profile.

For `mso_mdoc` presentation under the optional `openid4vp` profile, the response SHALL follow the mdoc processing rules of OpenID4VP v1.0.

#### **8.4.3.1 `mdoc-openid4vp` response requirements**

For the optional **`mdoc-openid4vp`** profile, the `vp_token` SHALL carry the base64url-encoded ISO `DeviceResponse` CBOR structure.

The <roles:Relying Party (RP)|Relying Party> is receiving a signed or MACed ISO presentation object that SHALL be validated against the originating request context and the reconstructed `SessionTranscript`.

The <roles:Relying Party (RP)|Relying Party> SHALL validate:

- `DeviceResponse` presence and format
- document type match between the request and the returned `DeviceResponse`
- <data-elements:Namespace|namespace> and requested element consistency
- request-response correlation
- <data-elements:Nonce|nonce> and handover consistency
- cryptographic binding of the returned mdoc presentation object against the reconstructed session context

#### **8.4.4 Error responses**

Where the presentation fails or cannot be completed, the Wallet SHALL return an error for `eu-eaap` through the encrypted `direct_post.jwt` response. The error SHOULD use a machine-readable form and, where appropriate, a human-readable description.

Error conditions include:

- invalid presentation
- malformed response
- user cancellation
- expired request
- unsupported credential format
- missing required proof material
- failed request-response correlation
- failed verifier-side validation

**Example (non-normative) decrypted `eu-eaap` success payload:**

```json
{
  "vp_token": "<presentation-response>",
  "state": "<transaction-state>"
}
```

The value transmitted to `response_uri` is the JWE in the `response` parameter, not this decrypted object.

**Example (non-normative) decrypted error payload:**

```json
{
  "error": "invalid_presentation",
  "error_description": "Presentation validation failed",
  "state": "<transaction-state>"
}
```

### **8.5 Wallet Metadata Interface**

**Direction:** <roles:Relying Party (RP)|Relying Party> → Wallet metadata endpoint  
**Purpose:** Optional discovery of Wallet presentation capabilities before a request is created

Wallet Metadata is OAuth 2.0 Authorization Server Metadata as defined by RFC 8414, with the OpenID4VP wallet-metadata parameters, including `vp_formats_supported`.

A Wallet SHOULD publish this metadata. A <roles:Relying Party (RP)|Relying Party> MAY retrieve it before creating a <artifacts:Presentation Request> in either the same-device or the cross-device flow.

The <roles:Relying Party (RP)|Relying Party> MAY skip retrieval when the Wallet’s capabilities are already known or configured. Failure to publish or retrieve Wallet Metadata SHALL NOT by itself make an otherwise valid `eu-eaap` transaction invalid when the <roles:Relying Party (RP)|Relying Party> can construct a request the Wallet supports.

Wallet Metadata is not `client_metadata` and it is not the signed <artifacts:Request Object>.

When `request_uri_method=post` is used, `wallet_metadata` in the POST body uses these same metadata parameters, as defined in Section 8.2.2. That POST is not a substitute for this optional pre-request read, and this read is not a substitute for POST.

### **8.6 Verifier Metadata Publication**

For `eu-eaap`, the verifier metadata required for the presentation exchange SHALL be the `client_metadata` inside the signed <artifacts:Request Object>, as defined in Section 8.4.2. OpenID4VP requires verifier metadata other than the request-signing public key to be taken from `client_metadata` when `client_id` uses `x509_hash`.

An independently published verifier-metadata endpoint is OPTIONAL and deployment-specific. This RFC does not require one. A deployment that publishes such an endpoint SHALL NOT use it to replace `client_metadata` in the <artifacts:Request Object>, and the Wallet SHALL NOT be required to retrieve it for `eu-eaap`.

## **9\. Privacy and Security Considerations**

Implementations conforming to this RFC SHOULD follow strong privacy and security practices consistent with OpenID4VP-based presentation flows and with the assurance requirements of the claimed profile.

`eu-eaap` includes the request, response, and proof rules in Sections 5.2, 7, and 8. This RFC still does not define a complete verifier-registration regime. It requires the RFC003 and RFC004 outcomes stated in Sections 6.1.5 and 7.2 before the parties rely on a request or a credential.

### **9.1 Data minimisation and disclosure control**

<roles:Relying Party (RP)|Relying Parties> SHOULD request only the minimum data necessary for the stated purpose of the transaction.

Wallets SHOULD support selective disclosure where supported by the selected credential format and SHOULD release only the claims, attributes, or credential-derived data necessary to satisfy the approved request.

Implementations SHOULD avoid requesting, presenting, transmitting, or retaining data beyond what is necessary for the use case.

When `transaction_data` is present, the Wallet shows it to the <roles:User> as part of consent. The transaction data is part of the same <roles:Relying Party (RP)|Relying Party> transaction as the credential request.

### **9.2 Request authenticity and integrity**

For `eu-eaap`, the Wallet SHALL validate the signed <artifacts:Request Object> before relying on it. Unsigned requests, requests passed by value, and requests whose signature does not verify with the `x5c` <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC> SHALL be rejected.

Wallets SHALL reject malformed or expired requests.

Registrar information and `client_metadata` support request processing, response encryption, and user transparency. Trustworthiness and registration status are the outcomes of RFC003 and RFC004, not a consequence of the parameters merely being present.

### **9.3 Replay protection, holder binding, and transaction binding**

For `eu-eaap`, the <artifacts:Request Object> SHALL contain <data-elements:Nonce|nonce>, `state`, and `aud`. The Wallet and the <roles:Relying Party (RP)|Relying Party> SHALL preserve those values across retrieval, presentation, and response validation.

Holder binding is a cryptographic proof by the credential holder. It is required when the credential and the request require it, and the SD-JWT form of that proof is the KB-JWT in Section 6.1.7. `state`, <data-elements:Nonce|nonce>, audience binding, and same-device browser correlation reduce replay and session-mixup risk. They do not replace holder binding.

When `transaction_data` is present, the KB-JWT `transaction_data_hashes` bind that data to the presentation and to the same originating transaction. The verifier SHALL reject a presentation whose hashes do not match that transaction.

A presentation response for one verifier session SHALL NOT be accepted in a different verifier session.

### **9.4 Response confidentiality and secure transport**

Implementers SHALL ensure secure transport for presentation requests, metadata retrieval, <artifacts:Request Object> retrieval, response submission, and related endpoint communication.

For `eu-eaap`, the authorization response SHALL be encrypted as specified in Section 8.4.2 and POSTed to `response_uri`. The algorithms are ECDH-ES, P-256, and `A128GCM` or `A256GCM`, using the verifier’s ephemeral key from `client_metadata`.

Response endpoints SHALL be protected against leakage, downgrade, redirection, and unauthorised access. The <roles:Relying Party (RP)|Relying Party> SHALL reject an `eu-eaap` response that arrives in the clear or through the browser.

### **9.5 Verifier impersonation and phishing resistance**

Wallets SHALL present the final <roles:Relying Party (RP)|Relying Party> identity and the purpose from the registrar information to the <roles:User> before consent for `eu-eaap`.

Cross-device invocation and same-device invocation SHOULD minimise phishing, request substitution, and verifier impersonation. The signed <artifacts:Request Object>, `x509_hash`, and the RFC003 authentication outcome are the request-authenticity checks. The same-device `redirect_uri` check is an additional session-binding check.

### **9.6 Credential-format considerations**

For **SD-JWT VC** presentation under `eu-eaap`, implementations SHALL preserve selective disclosure and SHALL validate the KB-JWT inputs in APT-PRES-VER-EAAP-05 when holder binding is required.

For `mso_mdoc` presentation under `eu-eaap` or `haip-vp`, implementations SHALL apply the mdoc-specific privacy, proof, and session-binding rules of OpenID4VP v1.0, ETSI TS 119 472-1, and the selected profile.

For the optional **`mdoc-openid4vp`** profile, implementations SHALL:

- protect the confidentiality and integrity of the returned `DeviceResponse` using the encrypted response mode defined by the ISO-aligned profile
- construct and validate the `SessionTranscript` correctly, since the `SessionTranscript` provides the binding between the OpenID4VP request context and the ISO mdoc presentation object
- validate the cryptographic integrity of the returned mdoc presentation object against the reconstructed `SessionTranscript` before relying on the returned data
- ensure that the `DeviceResponse` cannot be replayed in a different verifier session or bound to a different request context

Implementations claiming `mdoc-openid4vp` SHALL NOT treat mdoc presentation as a loosely profiled OpenID4VP format. The ISO session-binding, `DeviceResponse` structure, and cryptographic validation requirements are normative for that profile. Presenting `mso_mdoc` under `eu-eaap` does not by itself constitute an `mdoc-openid4vp` claim.

### **9.7 Logging, retention, and local protection**

Implementations SHOULD avoid logging sensitive presentation contents except where operationally necessary.

Where logs are required for security or troubleshooting purposes, implementations SHOULD minimise retained personal data and protect logs against unauthorised access.

Wallets, <roles:Relying Party (RP)|Relying Parties>, and related backend components SHOULD protect locally stored request, response, session, and metadata artefacts against unauthorised disclosure or modification.

### **9.8 Profile boundary**

This RFC defines protocol-level privacy and security expectations for interoperable presentation processing.

It does **not** by itself define:

- verifier trust-path, List of Trusted Entities, or Trust Anchor procedures
- mandatory possession of a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC> by every <roles:Relying Party (RP)|Relying Party>
- trusted-list supervision rules
- sector-specific legal reliance rules
- mandatory incident-handling obligations
- full deployment-security controls beyond the protocol boundary

RFC003 and RFC004 define the trust and status procedures whose outcomes this RFC requires. A future APTITUDE rule that every <roles:Relying Party (RP)|Relying Party> must hold a WRPRC would be an APTITUDE policy decision and would need to be stated as such.

## **10\. Conformance**

This RFC defines conformance for interoperable credential presentation and verification in APTITUDE using **OpenID4VP v1.0**. The mandatory presentation profile is `eu-eaap`; `haip-vp`, `openid4vp`, and `mdoc-openid4vp` are optional.

Conformance claims SHALL identify the supported presentation profile or profiles and the credential format or formats supported under each profile. The `eu-eaap`, `haip-vp`, and `openid4vp` profiles may be claimed with `dc+sd-jwt`, `mso_mdoc`, or both. The `mdoc-openid4vp` profile may be claimed only with `mso_mdoc`.

A claim of `eu-eaap` includes signed <artifacts:Request Object|Request Objects> passed by `request_uri`, `x509_hash`, `eu-eaap://` same-device invocation, ETSI registrar information, `direct_post.jwt` response encryption, and the holder-binding and transaction-data rules in Section 7. Those are part of `eu-eaap` conformance. They are not optional add-on claims, and they are not required of an implementation that claims only an optional profile.

This RFC does **not** require conformance to:

- JSON-LD W3C VC presentation
- a rule that every <roles:Relying Party (RP)|Relying Party> holds a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>
- the trust-path and status procedures themselves, which are specified by RFC003 and RFC004
- full ISO/IEC 18013-5 proximity device retrieval profiling
- sector-specific legal or supervisory rules

Conformance to `mdoc-openid4vp` includes its mdoc-specific invocation, request construction, session binding, `DeviceResponse` response structure, and verifier validation requirements. It does not include the `eu-eaap` requirements unless `eu-eaap` is also claimed.

### **10.1 Wallet conformance**

#### **10.1.1 `eu-eaap` wallet conformance**

An implementation conforms to this RFC as a **Wallet** under `eu-eaap` if it:

1. satisfies APT-PRES-WALLET-01 through APT-PRES-WALLET-15
2. satisfies APT-PRES-WALLET-EAAP-01 through APT-PRES-WALLET-EAAP-06. APT-PRES-WALLET-EAAP-07 is recommended and is not required for conformance
3. implements the `eu-eaap` interfaces in Sections 8.1, 8.2, 8.3, and 8.4. Section 8.5 Wallet Metadata publication is recommended and is not required for conformance
4. supports OpenID4VP v1.0 presentation processing together with the HAIP and ETSI TS 119 472-2 constraints of `eu-eaap`
5. supports the same-device and cross-device presentation flows in Section 6, including same-device `redirect_uri` completion and excluding that completion from cross-device
6. supports presentation of `dc+sd-jwt`, `mso_mdoc`, or both, and identifies the supported format or formats in its conformance claim
7. retrieves and validates signed <artifacts:Presentation Request|Presentation Requests> before acting on them
8. generates a KB-JWT for holder-bound SD-JWT VC presentations and encrypts the authorization response
9. submits the encrypted response to `response_uri` using `direct_post.jwt`

#### **10.1.2 `mdoc-openid4vp` wallet conformance**

An implementation conforms to this RFC as a **Wallet** under the optional `mdoc-openid4vp` profile if it:

1. satisfies APT-PRES-WALLET-01 through APT-PRES-WALLET-15 as applicable to the mdoc flow
2. satisfies APT-PRES-WALLET-MDOC-01 through APT-PRES-WALLET-MDOC-07
3. implements the ISO-aligned interfaces in Section 8, including Section 8.3.3.1, Section 8.3.5, and Section 8.4.3.1
4. supports same-device remote mdoc presentation using the `mdoc-openid4vp://` scheme
5. constructs the `SessionTranscript` correctly and binds the `DeviceResponse` to the originating request
6. generates a valid ISO `DeviceResponse` CBOR structure and encodes it as base64url in the `vp_token`
7. encrypts the response using the encrypted response mode defined by the ISO-aligned profile

`mdoc-openid4vp` wallet conformance does not require APT-PRES-WALLET-EAAP-01 through APT-PRES-WALLET-EAAP-07.

### **10.2 Verifier conformance**

#### **10.2.1 `eu-eaap` verifier conformance**

An implementation conforms to this RFC as a **<roles:Relying Party (RP)|Relying Party>** under `eu-eaap` if it:

1. satisfies APT-PRES-VER-01 through APT-PRES-VER-12, APT-PRES-VER-15, and APT-PRES-VER-16
2. satisfies APT-PRES-VER-EAAP-01 through APT-PRES-VER-EAAP-06
3. implements the `eu-eaap` interfaces in Section 8
4. supports OpenID4VP v1.0 presentation requests and `direct_post.jwt` response handling
5. supports the same-device and cross-device presentation flows in Section 6
6. supports presentation of `dc+sd-jwt`, `mso_mdoc`, or both, and identifies the supported format or formats in its conformance claim
7. creates signed <artifacts:Presentation Request|Presentation Requests> passed by `request_uri`
8. decrypts, correlates, and validates received presentation responses before relying on them, including KB-JWT and `transaction_data` checks
9. obtains the RFC003 and RFC004 credential trust and status outcomes before relying on returned credentials

#### **10.2.2 `mdoc-openid4vp` verifier conformance**

An implementation conforms to this RFC as a **<roles:Relying Party (RP)|Relying Party>** under the optional `mdoc-openid4vp` profile if it:

1. satisfies APT-PRES-VER-01 through APT-PRES-VER-12 as applicable to the mdoc flow
2. satisfies APT-PRES-VER-MDOC-01 through APT-PRES-VER-MDOC-10
3. implements the ISO-aligned interfaces in Section 8, including Section 8.3.3.1, Section 8.3.5, and Section 8.4.3.1
4. constructs the <artifacts:Presentation Request> using `format = mso_mdoc` with document type, <data-elements:Namespace|namespace>, and element identifiers
5. makes the request available using `request_uri`
6. reconstructs the `SessionTranscript` and validates the cryptographic binding of the returned `DeviceResponse`
7. validates `DeviceResponse` presence, format, document type match, <data-elements:Namespace|namespace> and element consistency, <data-elements:Nonce|nonce> and handover consistency, and cryptographic integrity

`mdoc-openid4vp` verifier conformance does not require the APT-PRES-VER-EAAP requirements.

### **10.3 Conformance boundaries**

Conformance to this RFC demonstrates protocol-level interoperability for presentation request processing, Wallet invocation, <artifacts:Request Object> retrieval, presentation submission, and verifier-side validation within the scope of the claimed presentation profile or profiles and credential format or formats.

Conformance to this RFC does **not** by itself demonstrate:

- compliance with the detailed trust procedures of RFC003 or the status procedures of RFC004, beyond the requirement to obtain their outcomes
- compliance with ARF v3.0.0, CIR 2024/2982, or CIR 2025/848 obligations beyond the protocol interoperability scope exercised here
- compliance with sector-specific supervisory or legal requirements
- compliance with the full ISO/IEC 18013-5 proximity device retrieval profile (ETSI TS 119 472-2 clause 5)
- compliance with ETSI requirements that are out of scope for this RFC, including API-mediated flows
- compliance with ISO/IEC TS 18013-7 requirements beyond the remote presentation scope defined by this RFC

### **10.4 Scope of the conformance matrix**

The conformance matrix defined by this RFC verifies protocol interoperability between the implementation under test and the reference endpoints or reference request/response patterns defined by this APTITUDE Presentation Profile.

It is intended to confirm correct support for representative OpenID4VP v1.0 presentation flows covered by this RFC, including the `eu-eaap` request, retrieval, encryption, holder-binding, and response behaviors in scope for the selected test scenarios.

The matrix is a **protocol interoperability matrix**, not a complete ARF v3.0.0, CIR 2024/2982, or CIR 2025/848 compliance assessment, and not a re-test of the RFC003 and RFC004 catalogues.

It focuses on:

- presentation request processing
- Wallet invocation and <artifacts:Request Object> retrieval
- presentation generation and encrypted submission
- request-response and same-device session correlation
- holder binding and transaction-data binding
- verifier-side response validation
- format-specific interoperability checks for the credential formats in scope

Credential Issuer and Attestation Provider trust-path, List of Trusted Entities, Trust Anchor, and status checks are required outcomes of the presentation flow. Their procedures are tested under RFC003 and RFC004.

For avoidance of doubt, the matrix in this version does not exercise ETSI clause 5 proximity `RequestInfo` transport. That ETSI mechanism remains outside the conformance scope of this RFC version.

Where ARF v3.0.0 or CIR identifiers are included, they provide traceability and alignment for the interoperability capability being exercised, rather than full normative coverage of the broader requirement domain.

### **10.5 Claims outside this RFC**

Signed <artifacts:Request Object|Request Objects>, `request_uri` retrieval, registrar information, encrypted `direct_post.jwt` responses, and SD-JWT KB-JWT validation are inside `eu-eaap` conformance. They are not additional claims outside this RFC.

If an implementation claims support for a further ecosystem profile layered on top of this RFC, that claim SHOULD be stated separately from RFC conformance.

Such additional claims MAY cover:

- rules for optional profiles that go beyond Section 5.6
- an APTITUDE decision, made later and stated as APTITUDE policy, that every <roles:Relying Party (RP)|Relying Party> must hold a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>
- ecosystem-specific legal or supervisory processing that RFC003 and RFC004 do not already define

Registrar information and a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)\|WRPRC> are handled as distinct objects. | CIR 2024/2982 Annex II OIDFVP-HAIP-COMMON-REQ-RO-13; CIR 2025/848; ARF v3.0.0 |
| `VP-CHECK-05` | DCQL request satisfaction | The Wallet returns a response matching the requested DCQL credential and claim constraints for the selected credential format and request profile. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-06` | Response and session correlation | The <roles:Relying Party (RP)\|Relying Party> receives the response at `response_uri`, decrypts it, and correlates it to the originating transaction using `state` and the transaction context. For same-device `eu-eaap`, it also correlates the `redirect_uri` return with the originating browser session. This correlation is not holder binding. Cross-device presentation does not use the redirect. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-07` | <data-elements:Nonce> binding | The request <data-elements:Nonce\|nonce> is present and is validated consistently in request processing and response validation. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-08` | SD-JWT KB-JWT validation | For a holder-bound SD-JWT presentation, the <roles:Relying Party (RP)\|Relying Party> validates the KB-JWT signature, `aud`, <data-elements:Nonce\|nonce>, `sd_hash`, and applicable `transaction_data_hashes`. A presentation without holder binding is accepted only when the request explicitly allows it for that credential. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-09` | Encrypted `direct_post.jwt` response | The Wallet encrypts the authorization response with ECDH-ES, P-256, and `A128GCM` or `A256GCM`, using the ephemeral key from `client_metadata`, and POSTs it to `response_uri` with `response_mode=direct_post.jwt`. The response does not travel through the browser. The <roles:Relying Party (RP)\|Relying Party> decrypts it. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-10` | Transaction-data binding | When `transaction_data` is present, the Wallet shows it during consent, generates the required hashes, and the <roles:Relying Party (RP)\|Relying Party> validates those hashes against the transaction data of the same originating transaction. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-11` | mdoc `DeviceResponse` validation | For ISO/IEC 18013-7 remote mdoc presentation, the <roles:Relying Party (RP)\|Relying Party> validates `DeviceResponse` presence and format, document type match, <data-elements:Namespace\|namespace> and element consistency, request-response correlation, <data-elements:Nonce\|nonce> and handover consistency, and cryptographic validation of the returned mdoc presentation object against the reconstructed `SessionTranscript`. | CIR 2024/2982 Art. 5 / Annex II (ISO/IEC 18013-7 Annex C); ARF v3.0.0 |
| `VP-CHECK-12` | Request-URI retrieval | The Wallet retrieves the signed <artifacts:Request Object> from `request_uri`. GET retrieval succeeds. When `request_uri_method=post` is used, the Wallet sends `wallet_nonce` and the signed <artifacts:Request Object> repeats it. POST is not required for this check. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-17` | `eu-eaap://` invocation | For `eu-eaap` same-device presentation, the Wallet is invoked with `eu-eaap://` and the Authorization Request carries `client_id`, `request_uri`, and `request_uri_method` when used. | CIR 2024/2982 Art. 5 / Annex II; ARF v3.0.0 |
| `VP-CHECK-18` | Registrar information and conditional WRPRC | For `eu-eaap`, the <artifacts:Request Object> carries ETSI registrar information in `verifier_info`. When the applicable registration or trust profile requires a <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)\|WRPRC>, that certificate is also carried in `verifier_info` and is validated under RFC003 and RFC004. A missing or invalid required WRPRC fails authorization. Registrar information and the WRPRC remain distinct objects. For `mdoc-openid4vp`, `verifier_info` carries registration material when that profile requires it; this check does not import the `eu-eaap` registrar-information rule into `mdoc-openid4vp`. | CIR 2024/2982 Annex II OIDFVP-HAIP-COMMON-REQ-RO-13; CIR 2025/848; ARF v3.0.0 |
| `VP-CHECK-13` | ISO mdoc invocation method | The Wallet is invoked using the `mdoc-openid4vp://` scheme for same-device remote mdoc presentation under the ISO/IEC 18013-7-aligned profile. | CIR 2024/2982 Art. 5 / Annex II (ISO/IEC 18013-7 Annex C); ARF v3.0.0 |
| `VP-CHECK-14` | ISO mdoc request structure | The <artifacts:Presentation Request> uses `format = mso_mdoc`, identifies the requested document type, and specifies <data-elements:Namespace\|namespace> and element identifiers compatible with ISO mdoc processing. | CIR 2024/2982 Art. 5 / Annex II (ISO/IEC 18013-7 Annex C); ARF v3.0.0 |
| `VP-CHECK-15` | ISO `SessionTranscript` binding | The Wallet constructs the `SessionTranscript` using the OpenID4VP-to-ISO handover mapping, and the <roles:Relying Party (RP)\|Relying Party> reconstructs and validates the same `SessionTranscript` inputs. The `DeviceResponse` is cryptographically bound to the originating request through the `SessionTranscript`. | CIR 2024/2982 Art. 5 / Annex II (ISO/IEC 18013-7 Annex C); ARF v3.0.0 |
| `VP-CHECK-16` | ISO mdoc encrypted response | The Wallet encrypts the mdoc presentation response using an encrypted response mode supported by the selected OpenID4VP mdoc profile. The <roles:Relying Party (RP)\|Relying Party> successfully decrypts and processes the response. | CIR 2024/2982 Art. 5 / Annex II (ISO/IEC 18013-7 Annex C); ARF v3.0.0 |
