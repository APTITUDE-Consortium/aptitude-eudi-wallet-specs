## **1 Introduction**

This document is part of **APTITUDE horizontal interoperability RFC** for credential issuance.

It establishes the baseline, cross-pilot profile to be used by APTITUDE pilots and technical implementations for the issuance of <credentials:Attestation|Attestations> in a consistent and testable manner.

This RFC profiles issuance based on:

- OpenID for Verifiable Credential Issuance (OpenID4VCI) 1.0  
- OpenID4VC High Assurance Interoperability Profile (HAIP) 1.0
- ETSI TS 119 472-3

against the ARF and CIR snapshot defined in Section 1.1.

The purpose of this document is to provide:

- a stable starting point for interoperability across APTITUDE pilots;
- a common baseline for Wallets, Issuers, and <components:Authorization Server|Authorisation Servers>;
- a requirements set that can be translated into **ITB+ conformance test suites**;
- a basis for pilot-specific issuance profiles that need stricter domain or credential-format constraints.

This specification focuses **only on issuance**. It covers wallet-initiated and issuer-initiated issuance, including both **Authorisation Code Flow** and **Pre-Authorised Code Flow**, together with the metadata, security bindings, and proof mechanisms needed to support interoperable issuance. **Interactive Authorization**, from the OpenID4VCI 1.1 editor's draft, is an optional authorisation path. It is not required for conformance.

This document does **not** define presentation or verifier behavior as such. Pilot-specific or Trust-Framework profiles MAY define additional issuance-side policy metadata.

### **1.1 Reference baseline**

For D2.1, this RFC uses the following architectural and legal snapshot. Later ARF or CIR revisions are out of scope unless a subsequent RFC revision explicitly updates this baseline.

- **ARF v3.0.0** (2026-07-21) is the Architecture and Reference Framework reference, in particular Annex 2 Topic 10 (*Issuing a PID or attestation to a Wallet Unit*). Subsequent mentions of “the ARF” in this RFC mean ARF v3.0.0.
- **CIR (EU) 2024/2982** (protocols and interfaces), as amended by **CIR (EU) 2026/1731**, is the issuance-protocol CIR. The applicable provisions are Article 4 and Annex I, which designate ETSI TS 119 472-3 V1.1.1 for issuance of PID and electronic attestations of attributes.
- **CIR (EU) 2024/2979** (integrity and core functionalities), as amended by **CIR (EU) 2026/1731**, is the Wallet Unit Attestation CIR. The applicable provisions are Article 6 and Annex Ib (Wallet Instance Attestation and Key Attestation).
- **CIR (EU) 2024/2977** (PID and EAA), as amended by **CIR (EU) 2026/1731**, applies where issuance-side PID or EAA constraints are relevant.

In the remainder of this RFC, the short forms **CIR 2024/2982**, **CIR 2024/2979**, and **CIR 2024/2977** mean those acts as amended by CIR (EU) 2026/1731. Generic “CIR” references without an identifier are not used.

## **2 Scope**

This specification defines:

- a baseline profile of OpenID4VCI for issuing <credentials:Attestation|Attestations>;
- requirements for Wallets that request, receive, validate, and store credentials;
- requirements for <roles:Attestation Provider (AP)|Attestation Provider|Credential Issuers> and their <components:Authorization Server|Authorisation Servers>;
- support for **wallet-initiated issuance** and **issuer-initiated issuance via <artifacts:Credential Offer>**;
- support for both **Authorisation Code** Flow and **Pre-Authorised Code Flow**;
- the minimum endpoints, metadata, and request-processing rules necessary to enable interoperable issuance;
- issuance-side requirements for wallet attestation, <processes:Proof of Possession|proof-of-possession>, <processes:Device Binding|device binding>, and deferred issuance;
- conditional notification handling where the selected deployment supports issuance notifications;
- processing of an optional embedded disclosure policy when the Issuer includes one, as defined by the APTITUDE Trust Framework and RFC-03;
- optional **Interactive Authorization** (OpenID4VCI 1.1) for Wallets and Issuers that implement it. Implementations that use only the OpenID4VCI 1.0 baseline remain conformant;

This document is intentionally **horizontal** and **cross-pilot**. It does not define credential-specific claim sets, domain schemas, or sector-specific assurance rules, except where a specific issuance profile requires explicit protocol-level constraints.

This document describes:

- issuance protocol flows;
- baseline security and privacy requirements;
- interfaces and endpoints, including Wallet invocation, <artifacts:Credential Offer>, PAR, Token, Credential, Deferred Credential, <data-elements:Nonce>, Notification, Authorization Challenge, and metadata endpoints where applicable;
- conformance requirements that can be mapped to ITB+ test cases.

### **2.1 Out of Scope**

The following are out of scope for this RFC:

- presentation and verification flows, except the presentation a Wallet returns to an Authorization Challenge Endpoint when optional Interactive Authorization (Section 7.8) is used. That exchange is specified only as far as issuance requires it. Presentations made to a <roles:Relying Party (RP)|Relying Party> remain in RFC-02;
- verifier requirements;  
- trust framework governance, federation policy, and trust-list operations, except where issuance processing requires validation against such trust material;
- credential-specific semantic profiles and domain-specific claim definitions;
- pilot-specific UX constraints;  
- business, legal, or organisational policy beyond the protocol-visible issuance requirements captured in metadata;
- credential reuse policy and its enforcement, including provision of an ETSI EAA reuse-policy parameter in Issuer metadata.

## **4 Roles and Components**

This specification uses the following roles:

- **Wallet Unit / Wallet**: The <components:Wallet Unit>, as defined in ARF v3.0.0 and the APTITUDE glossary, including its <components:Wallet Instance|Wallet Instances>, acting on behalf of the <roles:User> to request, receive, validate, store, and manage <credentials:Attestation|Attestations> and associated cryptographic material. Where the distinction between Wallet Unit and Wallet Instance is not material, this RFC uses the short term **Wallet**.  
- **<roles:User>**: As defined in the APTITUDE glossary: the natural person or legal representative controlling the Wallet and authorising credential issuance or presentation.  
- **<roles:Attestation Provider (AP)|Attestation Provider> (AP)**: As defined in the APTITUDE glossary and aligned with ARF v3.0.0: the entity that decides to issue <credentials:Attestation|Attestations> and operates, or is associated with, the issuance service.  
- **<components:Authorization Server|Authorisation Server> (AS)**: As defined in the APTITUDE glossary and aligned with ARF v3.0.0: the OAuth 2.0 / OpenID component responsible for authenticating the <roles:User> and issuing tokens authorising access to the Credential and related endpoints.

The <components:Authorization Server|Authorisation Server> MAY be co-located with the <roles:Attestation Provider (AP)|Attestation Provider> or MAY be operated separately.

## **5 Protocol Overview**

The APTITUDE issuance baseline is based on **OpenID4VCI 1.0**, constrained by **HAIP 1.0**, and aligned with the issuance-protocol requirements selected from **ETSI TS 119 472-3**. The ETSI-aligned requirements stated in this RFC are mandatory baseline requirements. ETSI reuse-policy requirements, including an EAA reuse policy in Issuer metadata, remain outside this RFC's scope. An Issuer MAY include an embedded disclosure policy. A Wallet SHALL process an embedded disclosure policy when the Issuer includes one, as defined by the APTITUDE Trust Framework and RFC-03.

The profile adopts the following baseline choices:

WIA, DPoP, and KA are separate protocol concepts. WIA authenticates the Wallet Instance as an OAuth client; DPoP sender-constrains OAuth requests and access tokens; and KA attests credential-binding key material at the Credential Endpoint. In this RFC, KA means the OpenID4VCI key-attestation object; for the ETSI-aligned baseline, it is the WUA profile of that object defined by ETSI TS 119 472-3.

Where WIA authentication and DPoP are both required for the same request, APTITUDE uses the combined mode defined in `draft-ietf-oauth-attestation-based-client-auth-11`. The request uses the `attest_jwt_client_auth_dpop` Token Endpoint authentication method and carries `OAuth-Client-Attestation: <WIA>` and `DPoP: <proof signed with the private key corresponding to WIA.cnf>`. The DPoP proof performs both the RFC 9449 sender-constraining function and the proof-of-possession function required for WIA-based client authentication; a separate Client Attestation PoP JWT is not required. The AS and Resource Server SHALL require a fresh nonce in DPoP proofs as defined in RFC 9449 and MAY issue `DPoP-Nonce` values independently of each other. Where the Wallet does not yet have a current nonce for that server, the server SHALL reject the request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header; the Wallet SHALL retry with that nonce in the DPoP proof. Authorization Server Metadata SHALL advertise `attest_jwt_client_auth_dpop` as a supported Token Endpoint authentication method and `dpop_combined` in `client_attestation_pop_methods_supported`.

- support for **Authorisation Code Flow** for issuance interactions requiring <roles:User> authentication and authorisation;
- support for **Pre-Authorised Code Flow** for issuer-initiated issuance scenarios where issuance is initiated through a <artifacts:Credential Offer> and the applicable grant is pre-authorised;
- support for **issuer-initiated issuance via <artifacts:Credential Offer>**;
- support for **wallet-initiated issuance**, where the Wallet selects a credential type or credential configuration and derives the corresponding request parameters from Issuer metadata;
- use of **Pushed Authorisation Requests (PAR)** for Authorisation Code Flow requests under this profile;
- use of **<protocols:PKCE> with `S256`** for Authorisation Code Flow;
- use of **<protocols:DPoP> as defined in RFC 9449** for sender-constraining access tokens and applicable HTTP requests;
- use of **<artifacts:Wallet Instance Attestation (WIA)>** as OAuth client authentication material at the PAR and Token endpoints;
- support for **<processes:Proof of Possession|proof-of-possession> / <processes:Key Binding|key binding>** during credential issuance;
- support for **Key Attestation (KA)** and `proofs` structures at the Credential Endpoint for device-bound issuance;
- support for **deferred issuance** where immediate issuance is not possible;
- support for issuance-side metadata defined by applicable APTITUDE or Trust-Framework profiles.

Wallets and Issuers SHALL support the `A128GCM` and `A256GCM` algorithms, in addition to the cryptographic suites required by OpenID4VC-HAIP.

The following ETSI-aligned issuance requirements apply:

- same-device Wallet invocation SHALL support the custom URL schemes `openid-credential-offer://` (OpenID4VCI), `haip-vci://` (HAIP), and `eu-eaa-offer://` (ETSI);
- Issuer Metadata SHALL be signed metadata as defined by OpenID4VCI, and the JWS protected header SHALL carry the Issuer access certificate (<artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>) in `x5c` as profiled by ETSI;
- Issuer Metadata SHALL support the `issuer_info` metadata parameter to transport issuer registration material (<artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>), including the registration certificate and registrar-provided registration information, as profiled by ETSI.

Providers shall support at least one of **`authorization_code`** or **`urn:ietf:params:oauth:grant-type:pre-authorized_code`** in the <artifacts:Credential Offer>. This RFC profiles both, and treats them as first-class issuance paths. PAR requirements apply only to the Authorisation Code Flow path.

**Interactive Authorization** is optional for Wallets and Issuers. It is a back-channel way to obtain an authorisation code, profiled on OAuth 2.0 for First-Party Applications and on the Interactive Authorization section of the OpenID4VCI 1.1 editor's draft. The <components:Authorization Server|Authorisation Server> publishes an Authorization Challenge Endpoint. The Wallet posts the authorisation request there, together with the interaction types it supports. The <components:Authorization Server|Authorisation Server> either returns an authorisation code or answers with the one interaction it requires. Where that interaction is a credential presentation, the Wallet returns the presentation to the same endpoint. The resulting authorisation code is redeemed at the Token Endpoint under Section 7.4.

Interactive Authorization is an alternative to PAR for obtaining an authorisation code. It does not apply to **Pre-Authorised Code Flow**. It does not change the PID authorisation rules in Section 6. An Issuer that needs the Holder to authenticate in a browser continues to use PAR and the Authorisation Endpoint. This RFC adopts Interactive Authorization only. It does not adopt the other OpenID4VCI 1.1 corrections, including `invalid_tx_code`, `credential_metadata` on the Credential Response, and Credential Issuer Identifier path normalisation. Those behaviours stay as specified by OpenID4VCI 1.0. OpenID4VCI 1.1 is an editor's draft. Where a published 1.1 text differs from the Interactive Authorization profile in this RFC, the published text prevails and this RFC is revised. Section 7.8.1 pins the readings used until then.

For Authorisation Code Flow, this profile assumes the Wallet interacts with the <components:Authorization Server|Authorisation Server> using PAR, receives an authorisation code, exchanges it at the Token Endpoint, and then calls the Credential Endpoint. Where the Wallet and the Issuer both support Interactive Authorization, the Wallet MAY obtain that authorisation code through the Authorization Challenge Endpoint (Section 6.4) instead of PAR. <artifacts:Wallet Instance Attestation (WIA)|WIA> is carried at the PAR endpoint, or at the Authorization Challenge Endpoint when that path is used, and again at the Token Endpoint, together with DPoP proof signed by the key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.

For device-bound issuance, ETSI requires the Credential Request to carry a `proofs` parameter containing either `jwt` or `attestation`. In the `jwt` mechanism, the Wallet proves possession of a key to be bound to the credential and carries the Key Attestation (KA) in the `key_attestation` protected header parameter. In the `attestation` mechanism, the Wallet carries the KA directly without separate proof of possession of each attested key. The Issuer's processing rules differ accordingly and are profiled in the normative sections below.

### **5.1 Credential Format Baseline**

This RFC defines the interoperability baseline at protocol level for the following formats only:

- **SD-JWT VC**;
- **ISO mdoc**.

Other credential formats, including JSON-LD variants and X.509-AC EAA, are outside this RFC unless another APTITUDE profile explicitly defines them. ETSI credential-format terminology used by such profiles is defined in **ETSI TS 119 472-1**.

To preserve a stable horizontal baseline, pilot-specific RFCs SHALL specify any additional constraints for a concrete credential format and SHALL NOT relax the mandatory requirements in this document.

### **5.2 Pilot-specific extensions**

Pilot-specific issuance RFCs MAY extend this profile with:

- concrete credential configuration identifiers;  
- claim set and schema rules;  
- assurance-level requirements;  
- format-specific proof rules;  
- issuance policy constraints.

Such extensions SHALL remain compatible with this baseline.

## **6 High-level Flows**

This section describes the high-level issuance interactions supported by this RFC.

This profile supports:

- **wallet-initiated issuance**;
- **issuer-initiated issuance via <artifacts:Credential Offer>**;
- **Authorisation Code Flow**;
- **Pre-Authorised Code Flow**;
- **immediate issuance** and **deferred issuance**;
- optional **Interactive Authorization**, where both the Wallet and the Issuer support it.

For issuance interactions using the **Authorisation Code Flow**, the Wallet uses **PAR** before user authorisation, unless both parties support Interactive Authorization and the Wallet uses Section 6.4. The Wallet sends **<artifacts:Wallet Instance Attestation (WIA)>** to the **PAR Endpoint**, or to the Authorization Challenge Endpoint when that path is used, and again to the **Token Endpoint**, with DPoP proof signed by the key referenced by the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.

For issuance interactions using the **Pre-Authorised Code Flow**, no PAR or authorisation redirect is required. The Wallet processes the <artifacts:Credential Offer>, redeems the pre-authorised grant at the Token Endpoint, and proceeds to the Credential Endpoint.

For PID issuance under the ETSI-aligned baseline, Pre-Authorised Code Flow user authorisation SHALL use physical presence. An APTITUDE profile requiring a high level of assurance for online PID issuance SHALL NOT use Pre-Authorised Code Flow.

For **device-bound issuance**, the Wallet sends a Credential Request containing a `proofs` structure as profiled by this RFC. The Credential Request carries **Key Attestation (KA)** at the Credential Endpoint, either in the protected header of `proofs.jwt[*]` or directly in `proofs.attestation[*]`, depending on the mechanism used.

Because this RFC is issuance-only, presentation and verifier behavior are not described here except for the presentation a Wallet returns during optional Interactive Authorization (Section 6.4), and where issuer-provided issuance metadata is needed by the Wallet for later use.

### **6.1 Wallet-initiated Issuance Flow**

**Actors**: <roles:User>, <roles:Attestation Provider (AP)|Attestation Provider> (including AS).

#### **6.1.1 Configuration and discovery**

1. Before initiating issuance, the Wallet SHALL obtain or use a valid cached copy of Credential Issuer Metadata and the applicable Authorization Server Metadata. The Wallet obtains Credential Issuer Metadata, including at minimum:
    - <roles:Attestation Provider (AP)|Attestation Provider> metadata;
    - supported credential configurations;
    - the mapping between offered credential configurations and the request parameters needed to initiate issuance;
    - supported grant types;
    - supported proof methods and the OpenID4VCI `c_nonce` retrieval mechanism;
2. The Wallet determines the Authorization Server identifier from Credential Issuer Metadata. If `authorization_servers` is present, the Wallet uses the selected grant's `authorization_server` hint only when the array contains multiple Authorization Server identifiers. The hint value MUST match an entry in the `authorization_servers` array; if it is present when the array does not contain multiple entries, or does not match an entry, the Wallet SHALL treat the Credential Offer as invalid. If no valid hint is present, the Wallet selects the applicable Authorization Server from the array. If `authorization_servers` is absent, it uses the Credential Issuer identifier as the Authorization Server issuer identifier. The Wallet obtains the corresponding Authorization Server Metadata and uses it to discover the Token Endpoint, PAR Endpoint, supported DPoP signing algorithms, including `dpop_signing_alg_values_supported`, and combined-attestation support. From the same Authorization Server Metadata document the Wallet reads `authorization_challenge_endpoint` and `require_interactive_authorization`.
3. The Wallet retrieves and processes signed Issuer Metadata carrying:
   - the Issuer access certificate (<artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>) in the JWS `x5c` protected header; and
   - the `issuer_info` metadata parameter for issuer registration material (<artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>).
4. If no valid cached metadata exists, or if endpoints or advertised capabilities have changed, the Wallet refreshes the relevant metadata before continuing. The Wallet selects the issuance path:
    - **Pre-Authorised Code Flow**, where the offer or the selected configuration uses `urn:ietf:params:oauth:grant-type:pre-authorized_code`. Interactive Authorization does not apply to this grant.
    - **Authorisation Code Flow** through the Authorization Challenge Endpoint (Section 6.4), where Authorization Server Metadata contains `authorization_challenge_endpoint` and either `require_interactive_authorization` is `true`, or the Wallet supports Interactive Authorization and selects that path.
    - **Authorisation Code Flow** through PAR (Section 6.1.3) for every other Authorisation Code Flow transaction.
5. Where `require_interactive_authorization` is `true` and `authorization_challenge_endpoint` is absent, the Wallet SHALL treat the Authorization Server Metadata as invalid. Where `require_interactive_authorization` is `true` and the Wallet does not implement Interactive Authorization, the Wallet SHALL NOT continue with that <components:Authorization Server|Authorisation Server>. If Credential Issuer Metadata lists more than one Authorization Server, the Wallet MAY select another server that does not require Interactive Authorization. Where `authorization_challenge_endpoint` is absent, or `require_interactive_authorization` is absent or `false`, a Wallet that does not implement Interactive Authorization ignores both parameters and uses PAR for Authorisation Code Flow.

#### **6.1.2 User selects credential**

1. The <roles:User> chooses a credential type or credential configuration.
2. The Wallet identifies the corresponding credential configuration and the applicable issuance path.
3. Where Section 6.1.1 selected wallet-initiated **Authorisation Code Flow** through the Authorization Challenge Endpoint, the Wallet continues at Section 6.4. Where it selected wallet-initiated **Authorisation Code Flow** through PAR, the Wallet prepares an authorisation request as defined in Section 6.1.3.

#### **6.1.3 Pushed Authorisation Request (PAR)**

This section applies when Section 6.1.1 selected Authorisation Code Flow through PAR.

1. For that path, the Wallet constructs an authorisation request containing at minimum:
   - `client_id`;
   - the relevant `scope`, `authorization_details`, or other profiled authorisation parameters;
   - `code_challenge` using <protocols:PKCE> `S256`;
   - `redirect_uri`;
   - `response_type=code`;
   - `state`;  
   - the required credential-related authorisation parameters.
2. The Wallet sends the request to the Issuer's **PAR Endpoint**.
3. The Wallet includes:
   - the <artifacts:Wallet Instance Attestation (WIA)|WIA> at the PAR request; and
   - a DPoP proof signed by the key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
4. If the Wallet does not have a current AS DPoP nonce, it still sends the PAR request. The PAR Endpoint SHALL reject that request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header. The Wallet SHALL place that nonce in the `nonce` claim of a new DPoP proof and repeat the PAR request.
5. Once the request carries a valid DPoP nonce, the PAR Endpoint validates the request and returns a `request_uri` and validity information. A successful response MAY include a `DPoP-Nonce` HTTP header carrying the nonce to use on the next request to this <components:Authorization Server|Authorisation Server>.

#### **6.1.4 User authorisation**

1. The Wallet directs the <roles:User> to the Authorisation Endpoint using the `request_uri` obtained from PAR.
2. The <roles:User> authenticates according to the Issuer's policy. For APTITUDE, that policy SHALL be either a separate OpenID4VP session or an alternative authentication method that does not use an EUDI Wallet.
3. The <roles:User> authorises the issuance transaction.
4. The <components:Authorization Server|Authorisation Server> redirects back to the Wallet with an authorisation `code` and `state`.

#### **6.1.5 Token request**

1. The Wallet sends a token request to the Token Endpoint, including:
   - `grant_type=authorization_code`;
   - `code`;
   - `redirect_uri`;
   - `code_verifier`;
   - WIA-based client authentication and a DPoP proof.
2. The Wallet includes:
   - the <artifacts:Wallet Instance Attestation (WIA)|WIA> at the Token Endpoint; and
   - a DPoP proof signed by the key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
3. If the Wallet does not have a current AS DPoP nonce, the Token Endpoint SHALL reject the request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header. The Wallet SHALL place that nonce in the `nonce` claim of a new DPoP proof and repeat the Token Request.
4. The Token Endpoint validates the request and returns:
   - a sender-constrained `access_token` whose confirmation member contains `cnf.jkt` holding the JWK thumbprint of the DPoP public key;
   - optional `refresh_token` or other explicitly defined OAuth/OpenID4VCI parameters;
   - a `DPoP-Nonce` HTTP response header when the AS issues a nonce for the next request.

#### **6.1.6 Credential request**

1. After receiving the Token response and immediately before generating credential proof material, the Wallet obtains two independent nonces:
   - a fresh OpenID4VCI `c_nonce` from the JSON body of the Issuer's **<data-elements:Nonce> Endpoint** response, included in the credential proof or KA; and
   - a Resource Server `DPoP-Nonce` from the `DPoP-Nonce` HTTP header on that response, included in the `nonce` claim of the DPoP proof for the Credential Endpoint.
   These values SHALL NOT be substituted for each other. If the Wallet does not yet have a Resource Server `DPoP-Nonce`, it still obtains `c_nonce` as above and proceeds to the next step.
2. The Wallet sends a request to the Credential Endpoint containing:
   - `Authorization: DPoP {access_token}`;
   - a DPoP proof bound to the access-token key, including the current Resource Server `DPoP-Nonce` when the Wallet has one;
   - the requested credential configuration or other format-specific request parameters;
   - a `proofs` structure or equivalent proof material, according to the selected proof mechanism, carrying the OpenID4VCI `c_nonce`.
   If the Wallet does not have a current Resource Server `DPoP-Nonce`, the Credential Endpoint SHALL reject the request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header. The Wallet SHALL include that nonce in a new DPoP proof and resubmit the Credential Request. The `c_nonce` in the credential proof or KA is unchanged by that retry.
3. For **device-bound issuance**, the request SHALL include issuance proof material that binds the issued credential to Wallet-controlled key material.
4. Where the selected proof method is based on `proofs.jwt`:
   - the Wallet proves possession of the private key to be bound to the credential; and
   - the Wallet carries the **Key Attestation (KA)** in the protected header parameter profiled for key attestation.
5. Where the selected proof method is based on `proofs.attestation`:
   - the Wallet carries the **Key Attestation (KA)** directly in the attestation structure; and
   - the Issuer processes the request according to the rules applicable to attested keys under the selected profile.
6. The <roles:Attestation Provider (AP)|Attestation Provider> validates:
   - the access token and its sender-constraining mechanism;
   - the credential request syntax;
   - the OpenID4VCI `c_nonce` and proof material;
   - the applicable wallet attestation material;
   - any credential-specific prerequisites.
7. The Issuer returns the credential immediately, or signals deferred issuance.

#### **6.1.7 Storage**

1. The Wallet validates the returned credential and associated metadata.
2. The Wallet stores the credential under <roles:User> control.
3. The Wallet stores issuer-provided metadata required by this RFC or another referenced APTITUDE or Trust-Framework profile. Where the Issuer includes an embedded disclosure policy, the Wallet stores and processes that policy as defined by the APTITUDE Trust Framework and RFC-03.

### **6.2 Issuer-initiated Issuance via Credential Offer**

In the issuer-initiated flow, the Issuer first decides to issue and then provides a **<artifacts:Credential Offer>** that the Wallet uses to continue the issuance process.

**Actors**: <roles:User>, Wallet, Issuer, optionally <components:Authorization Server|Authorisation Server>.

#### **6.2.1 Issuance decision**

1. The <roles:User> interacts with the Issuer in a business process such as onboarding, enrolment, registration, or completion of an eligibility step. Where the Issuer will use **Pre-Authorised Code Flow**, this step includes <roles:User> authentication, using a separate OpenID4VP session or an alternative non-EUDI Wallet method.
2. Following successful checks, the Issuer decides to issue one or more credentials. Where **Pre-Authorised Code Flow** is used, the Issuer generates the `pre-authorized_code` for the <artifacts:Credential Offer> and, where a transaction code is required, delivers that code to the <roles:User> through a channel separate from the <artifacts:Credential Offer>.

#### **6.2.2 Credential Offer creation**

1. The Issuer constructs a <artifacts:Credential Offer> that includes at minimum:
   - the `credential_issuer` identifier;
   - one or more offered credential identifiers or credential configurations;
   - grant information for one or more supported issuance paths;
   - the authorisation parameters or pre-authorised grant information needed by the Wallet to continue the flow.
2. The <artifacts:Credential Offer> MAY support either:
   - **Authorisation Code Flow**;
   - **Pre-Authorised Code Flow**; or
   - both.

#### **6.2.3 Credential Offer delivery and Wallet invocation**

1. The Issuer delivers the offer to the <roles:User> by one of:
   - displaying a QR code;  
   - providing a link;  
   - invoking a same-device Wallet using a supported Wallet invocation mechanism.
1. Issuers and Wallets **SHALL** support both **same-device** and **cross-device** delivery of <artifacts:Credential Offer|Credential Offers>.
1. For **same-device**, implementations **SHALL** support the custom URL schemes `openid-credential-offer://` (OpenID4VCI), `haip-vci://` (HAIP), and `eu-eaa-offer://` (ETSI).
1. For **cross-device**, implementations **SHALL** support delivery through a QR code carrying a valid <artifacts:Credential Offer> URI.

#### **6.2.4 Wallet processes the offer**

1. The Wallet receives the <artifacts:Credential Offer>.
1. The Wallet parses the offer and determines:
   - the Issuer base URL;  
   - offered credential configurations;  
   - applicable grant information;  
   - required authorisation parameters.
1. The Wallet displays the offer to the <roles:User> and asks for confirmation to proceed.

#### **6.2.5 Authorisation Code Flow variant**

1. Where the <artifacts:Credential Offer> uses **Authorisation Code Flow**, the Wallet first obtains Credential Issuer Metadata and Authorization Server Metadata as defined in Section 6.1.1. The offer supplies the `credential_issuer` identifier and grant information; it does not replace discovery. The same step selects PAR or the Authorization Challenge Endpoint.
2. Where Section 6.1.1 selected the Authorization Challenge Endpoint, the Wallet continues at Section 6.4, including `issuer_state` from the offer when the `authorization_code` grant carries it, and then continues at the Token Request (Section 6.1.5).
3. Otherwise the Wallet initiates the authorisation process using **PAR**, and follows Section 6.1 for:
   - PAR, including DPoP nonce bootstrap as in Section 6.1.3;
   - user authorisation;
   - token acquisition;
   - credential request;
   - storage.
4. The Wallet sends <artifacts:Wallet Instance Attestation (WIA)|WIA> at the PAR Endpoint when that path is used, at the Authorization Challenge Endpoint when Section 6.4 is used, and at the Token Endpoint on either path.

#### **6.2.6 Pre-Authorised Code Flow variant**

1. Where the <artifacts:Credential Offer> uses **Pre-Authorised Code Flow**, the Wallet does not perform a PAR request or browser-based authorisation redirect.
2. The Wallet sends a token request to the Token Endpoint including:
   - `grant_type=urn:ietf:params:oauth:grant-type:pre-authorized_code`;
   - the `pre-authorized_code`;
   - a transaction code or user code where required by the offer or by the applicable profile;
   - WIA-based client authentication and DPoP sender-constraining material.
3. If the Wallet does not have a current AS DPoP nonce, the Token Endpoint SHALL reject the request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header. The Wallet SHALL place that nonce in the `nonce` claim of a new DPoP proof and repeat the Token Request.
4. The Token Endpoint validates the pre-authorised grant and returns:
   - a sender-constrained `access_token` whose confirmation member contains `cnf.jkt` holding the JWK thumbprint of the DPoP public key;
   - optional `refresh_token` or other explicitly defined OAuth/OpenID4VCI parameters;
   - a `DPoP-Nonce` HTTP response header when the AS issues a nonce for the next request.
5. The Wallet then proceeds to the Credential Endpoint as defined in Section 6.1.6.

#### **6.2.7 Credential request**

1. The Wallet sends a Credential Request or Batch Credential Request to the Credential Endpoint.
2. The request includes:
   - `Authorization: DPoP {access_token}` and a DPoP proof bound to the access-token key;
   - the requested credential configuration information;
   - the applicable proof material;
   - Key Attestation (KA) where required by the selected proof method.
3. The Issuer validates the request and either returns the credential or initiates deferred issuance.

#### **6.2.8 Deferred issuance continuation**

1. If issuance cannot be completed immediately, the Issuer returns the information required for deferred retrieval.
2. The Wallet stores the transaction state and continues as defined in Section 6.3.

### **6.3 Deferred Credential Request**

Deferred issuance allows the Issuer to complete credential production asynchronously while preserving the issuance transaction state.

1. Where the Credential Endpoint cannot immediately return the credential, the Issuer returns the information needed for later retrieval, such as a transaction identifier and any endpoint or polling details required by the profile.
2. The Wallet stores the deferred issuance state.
3. The Wallet later calls the **Deferred Credential Endpoint** using the required access token and deferred issuance reference.
4. The Issuer either:
   - returns the issued credential;
   - indicates that issuance is still pending; or
   - returns an error if the deferred issuance transaction cannot be completed.
5. The Wallet repeats the retrieval only in accordance with the Issuer's indicated retry or polling guidance.
6. Once the credential is returned, the Wallet validates and stores it as in Section 6.1.7.

### **6.4 Interactive Authorization Flow**

This flow is optional. It applies when the Wallet and the Issuer both support Interactive Authorization and the Wallet uses it to obtain an authorisation code. A Wallet that does not implement it uses Sections 6.1 and 6.2.

**Actors**: <roles:User>, Wallet, Issuer (including the <components:Authorization Server|Authorisation Server>).

1. The Wallet uses the Authorization Challenge Endpoint selected in Section 6.1.1. This flow applies only after that discovery. Where `authorization_challenge_endpoint` is absent, the Wallet uses PAR for Authorisation Code Flow and does not use this flow.
2. The Wallet sends an initial Authorization Challenge Request. The request carries the credential-related authorisation parameters, `interaction_types_supported`, <protocols:PKCE> `S256`, <artifacts:Wallet Instance Attestation (WIA)|WIA>, and a DPoP proof. Where the Wallet is continuing an issuer-initiated issuance and the <artifacts:Credential Offer> carries `issuer_state` on the `authorization_code` grant, the request also carries that `issuer_state`.
3. The <components:Authorization Server|Authorisation Server> either returns an authorisation code, or responds with HTTP 403 and `insufficient_authorization`, naming exactly one `interaction_type_required` that the Wallet listed.
4. Where the required interaction is `urn:openid:dcp:ia:openid4vp_presentation`, the Wallet checks the presentation request, obtains <roles:User> consent, and posts the presentation back to the same Authorization Challenge Endpoint with the `auth_session` from the challenge response.
5. Where the required interaction is `urn:openid:dcp:ia:auth_via_web`, the Wallet opens the returned `request_uri` in an external user agent and continues as defined in Section 7.8.
6. When the <components:Authorization Server|Authorisation Server> returns an authorisation code, the Wallet continues at the Token Request (Section 6.1.5) and then the Credential Request (Section 6.1.6). Deferred issuance, where used, continues at Section 6.3.

## **7 Normative Requirements**

This section defines the baseline normative requirements for APTITUDE implementations of the issuance profile.

Unless otherwise stated, the requirements in this section apply to issuance interactions only.

### **7.1 Common requirements (Wallet and Issuer)**

Both Wallet and Issuer **SHALL**:

1. Support OpenID4VCI 1.0 for credential issuance.
2. Support metadata-based discovery.
3. Support wallet-initiated issuance.
4. Support issuer-initiated issuance via <artifacts:Credential Offer>.
5. Support at least one of the following issuance grant types:
   - **Authorisation Code Flow**;
   - **Pre-Authorised Code Flow**.
6. Support **Authorisation Code Flow** where the deployment requires <roles:User> authentication and interactive authorisation.
7. Support **Pre-Authorised Code Flow** where the deployment profile or issuance scenario permits issuer-initiated issuance without an interactive authorisation redirect.
8. Support DPoP as defined in RFC 9449 for sender-constraining access tokens and applicable HTTP requests.
9. Support <processes:Proof of Possession|proof-of-possession> / holder-binding during issuance, as required by the selected credential format and binding model.
10. Support issuance-time metadata required to construct and process issuance requests.
11. Support deferred issuance where the selected deployment profile or issuance process cannot always return the credential synchronously.
12. Support the `A128GCM` and `A256GCM` algorithms in addition to the cryptographic suites required by OpenID4VC-HAIP.
13. Support same-device Wallet invocation using the custom URL schemes `openid-credential-offer://`, `haip-vci://`, and `eu-eaa-offer://`.

Both Wallet and Issuer **SHOULD**:

1. Support both immediate and deferred issuance responses.
2. Support Batch Credential Requests where required by a more specific pilot or credential profile.
3. If the Wallet supports issuance notifications and receives a `notification_id` from the Issuer, support one or more Notification Requests for that `notification_id` in accordance with the applicable notification mechanism.

For issuance interactions using **Authorisation Code Flow**, both Wallet and Issuer **SHALL** additionally:

1. Support **Pushed Authorisation Requests (PAR)**.
2. Support <protocols:PKCE> with the `S256` code challenge method.
3. Support <artifacts:Wallet Instance Attestation (WIA)|Wallet Instance Attestation> handling at the PAR and Token endpoints.

### **7.2 Credential Offer**

Issuers **SHALL**:

1. Support <artifacts:Credential Offer|Credential Offers> for issuer-initiated issuance.
2. Include the `credential_issuer` identifier in the <artifacts:Credential Offer>.
3. Include one or more offered credential identifiers or credential configuration identifiers sufficient for the Wallet to determine what is being offered.
4. Include the grant information required by the Wallet to continue issuance.
5. Support at least one of the following grant types in <artifacts:Credential Offer|Credential Offers>:
   - `authorization_code`;
   - `urn:ietf:params:oauth:grant-type:pre-authorized_code`.
6. Include all grant-specific parameters needed by the Wallet to continue the flow.
7. Ensure that the <artifacts:Credential Offer> can be resolved consistently against Issuer metadata.
8. For same-device invocation, support delivery using the custom URL schemes `openid-credential-offer://`, `haip-vci://`, and `eu-eaa-offer://`.

Issuers **SHOULD**:

1. Support both same-device and cross-device offer delivery.
2. Support QR-code-based delivery and URI-based invocation.
3. Support <artifacts:Credential Offer|Credential Offers> containing multiple offered credential configurations where the issuance scenario requires this.

Wallets **SHALL**:

1. Be able to parse <artifacts:Credential Offer|Credential Offers> compliant with the applicable OpenID4VCI profile.
2. Extract the Issuer identifier, offered credential configurations, and grant information.
3. Determine from the offer whether the issuance path uses:
   - Authorisation Code Flow;
   - Pre-Authorised Code Flow; or
   - both.
4. Use the <artifacts:Credential Offer> information consistently in later token and credential requests.
5. Support same-device receipt via a supported Wallet invocation method.
6. Support cross-device receipt via a QR code carrying a valid <artifacts:Credential Offer> URI.
7. Support same-device receipt via the custom URL schemes `openid-credential-offer://`, `haip-vci://`, and `eu-eaa-offer://`.

Wallets **SHOULD**:

1. Validate that the offered credential identifiers or configurations are supported by the Issuer metadata before proceeding.
2. Present the <artifacts:Credential Offer> to the <roles:User> in a way that makes the offered credentials and issuing party clear.

### **7.3 Authorisation Endpoint and PAR**

This section applies to **Authorisation Code Flow** transactions that use PAR. It does not apply to a transaction that obtains the authorisation code through Interactive Authorization (Section 7.8). A front-channel authorisation request that presents a `request_uri` issued by the Authorization Challenge Endpoint is processed under Section 7.8.

Issuers **SHALL**:

1. Expose a PAR endpoint for issuance transactions using Authorisation Code Flow.
2. Require PAR for all authorisation requests under this profile.
3. Reject direct front-channel authorisation requests not preceded by PAR.
4. Require the Wallet to include the credential-related authorisation parameters needed for the selected credential configuration and issuance path.
5. Require <protocols:PKCE> with `S256`.
6. Require consistent use of `client_id` across PAR and Token requests.
7. Require <artifacts:Wallet Instance Attestation (WIA)> at the PAR endpoint.
8. Require a DPoP proof signed by the private key corresponding to the public key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
9. Verify that the <artifacts:Wallet Instance Attestation (WIA)|WIA> signature validates under the <roles:Wallet Provider (WP)> public key from the applicable trusted list.
10. Verify that the <artifacts:Wallet Instance Attestation (WIA)|WIA> is not expired.
11. Verify the DPoP proof under the public key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
12. Require a fresh DPoP nonce in the DPoP proof. If the Wallet does not present a current nonce, reject the PAR request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header carrying the nonce the Wallet must use on retry.

Wallets **SHALL**:

1. Use PAR for all Authorisation Code Flow requests under this profile.
2. Include the required credential-related authorisation parameters.
3. Include `client_id`, `response_type=code`, `redirect_uri`, `state`, and <protocols:PKCE> parameters.
4. Include <artifacts:Wallet Instance Attestation (WIA)|WIA> at the PAR endpoint.
5. Include a DPoP proof signed by the key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
6. Ensure that `client_id` is used consistently across PAR and Token requests.
7. When the PAR Endpoint returns `use_dpop_nonce` with a `DPoP-Nonce` HTTP header, place that nonce in the `nonce` claim of a new DPoP proof and repeat the PAR request.

Wallets **SHOULD**:

1. Check metadata in advance to determine whether additional authorisation parameters or `authorization_details` are required.
2. Treat expired or rejected <artifacts:Wallet Instance Attestation (WIA)|WIA> material as a recoverable client-authentication failure and obtain fresh attestation material before retrying.

### **7.4 Token Endpoint and Wallet Attestation**

This section applies to **Authorisation Code Flow**, including an authorisation code obtained through Interactive Authorization, and to **Pre-Authorised Code Flow**.

For **Authorisation Code Flow**, Wallets **SHALL**:

1. Send a Token Request containing:
   - `grant_type=authorization_code`;
   - `code`;
   - `redirect_uri`;
   - `code_verifier`.
2. Include <artifacts:Wallet Instance Attestation (WIA)|WIA> at the Token Endpoint.
3. Include a DPoP proof signed by the key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim.
4. Ensure consistency between the authenticated Wallet identity and the `client_id` used earlier in the transaction.

For **Pre-Authorised Code Flow**, Wallets **SHALL**:

1. Send a Token Request containing:
   - `grant_type=urn:ietf:params:oauth:grant-type:pre-authorized_code`;
   - the `pre-authorized_code`;
   - any transaction code or user code required by the offer or deployment profile.
2. Include <artifacts:Wallet Instance Attestation (WIA)|WIA> and a DPoP proof signed by the key referenced in its `cnf` claim.
3. Use the returned access token consistently in subsequent credential requests.

Issuers **SHALL**:

1. Expose a Token Endpoint.
2. Validate the Token Request according to the applicable grant type.
3. For Authorisation Code Flow, validate <protocols:PKCE> inputs and authorisation-code state as required by OAuth/OpenID4VCI.
4. Validate <artifacts:Wallet Instance Attestation (WIA)|WIA> and its associated DPoP proof:
   - the <artifacts:Wallet Instance Attestation (WIA)|WIA> signature under the <roles:Wallet Provider (WP)> public key from the applicable trusted list;
   - the <artifacts:Wallet Instance Attestation (WIA)|WIA> expiry;
   - the DPoP proof under the public key referenced in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim;
   - the DPoP `htm`, `htu`, `iat`, `jti`, and nonce claims as required by RFC 9449.
5. Issue sender-constrained access tokens whose confirmation member contains `cnf.jkt` holding the JWK thumbprint of the DPoP public key.
6. Bind token usage to the Wallet according to the selected sender-constraining mechanism.
7. Expose the OpenID4VCI Nonce Endpoint and require a fresh `c_nonce` from that endpoint for Credential Endpoint proof freshness. A `c_nonce` returned through another response, including a Token Response, SHALL NOT replace the Nonce Endpoint mechanism defined by this profile.
8. Require a fresh DPoP nonce in Token Request DPoP proofs. If the Wallet does not present a current nonce, reject the Token Request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header. A successful response SHALL include a `DPoP-Nonce` HTTP header when a new nonce is issued for the next request.

Wallets SHALL obtain a fresh OpenID4VCI c_nonce from the Issuer's Nonce Endpoint immediately before generating Credential Endpoint proof material and SHALL NOT rely on a c_nonce received in a Token Response for that purpose.

Issuers **SHOULD**:

1. Support refresh tokens where long-lived issuance processes, renewal, or deferred issuance need them.
2. Consider the sensitivity of the credential type before issuing long-lived refresh tokens.

Wallets **SHALL**:

1. Support sender-constrained token usage in subsequent calls to the Credential Endpoint.
2. When the <components:Authorization Server|Authorisation Server> or Resource Server returns `use_dpop_nonce` with a `DPoP-Nonce` HTTP header because a fresh DPoP nonce is required, including on the first request of a new issuance transaction, place that nonce in the `nonce` claim of a new DPoP proof and repeat the request. The Wallet obtains OpenID4VCI `c_nonce` from the Nonce Endpoint before generating credential proof material. `DPoP-Nonce` and `c_nonce` are separate values.

### **7.5 Credential Endpoint**

Issuers **SHALL**:

1. Expose a Credential Endpoint.
2. Support issuance requests for the credential configurations published in Issuer metadata.
3. Validate the access token and sender constraint.
4. Validate the credential request syntax and requested credential configuration.
5. For device-bound issuance, require the `proofs` parameter.
6. Require that `proofs` contain either:
   - the `jwt` child member; or
   - the `attestation` child member.
7. Validate the OpenID4VCI `c_nonce` and proof material according to the selected proof method.
8. Validate Key Attestation (KA) according to the selected proof method before issuing a device-bound credential.
9. Where applicable regulatory or trust rules provide KA status information, validate that status before issuing a device-bound credential and ensure that the issued credential does not outlive the relevant WIA or KA status-maintenance commitments.
10. Return either the issued credential or a deferred issuance response.
11. Require a fresh DPoP nonce in Credential Endpoint DPoP proofs. If the Wallet does not present a current Resource Server nonce, reject the request with error code `use_dpop_nonce`, as defined in RFC 9449, and a `DPoP-Nonce` HTTP header.

Wallets **SHALL**:

1. Send a Credential Request containing the requested credential configuration or other format-specific request parameters.
2. For device-bound issuance, include the `proofs` parameter.
3. Populate `proofs` using either:
   - `proofs.jwt`; or
   - `proofs.attestation`;
  according to the selected binding model and issuer requirements.
4. Obtain and use a fresh OpenID4VCI `c_nonce` from the Issuer's <data-elements:Nonce> Endpoint immediately before generating credential proof material.
5. Include a DPoP proof in the Credential Endpoint request, using the access-token-bound key and a current Resource Server `DPoP-Nonce`, including a `DPoP-Nonce` returned on the <data-elements:Nonce> Endpoint response when present. If the Credential Endpoint returns `use_dpop_nonce` with a `DPoP-Nonce` HTTP header, include that nonce in a new DPoP proof and retry. The `c_nonce` in the credential proof or KA is unchanged by that retry.
6. Validate the returned credential, including issuer binding and format-specific integrity checks.
7. Store only credentials that have successfully passed Wallet validation.

### **7.5.1 Credential Request using `proofs.jwt`**

Wallets **SHALL**:

1. Include exactly one element in the `jwt` array.
2. Include a valid OpenID4VCI `c_nonce` claim in the proof JWT body, obtained from the Issuer's <data-elements:Nonce> Endpoint.
3. Include the `key_attestation` protected header parameter.
4. Carry the Key Attestation (KA) in that `key_attestation` parameter and include the same issuer-provided `c_nonce` in the KA's `nonce` claim.
5. Ensure that the KA contains one or more attested public keys owned by the <components:Wallet Unit>.
6. Sign the JWT using the private key corresponding to the first public key in the `attested_keys` claim of the KA.

Issuers **SHALL**:

1. Verify that the KA signature in `key_attestation` validates under the <roles:Wallet Provider (WP)> public key from the applicable trusted list.
2. Verify that the JWT signature validates under the first public key in the `attested_keys` array of the KA.
3. Verify that the proof JWT contains a valid OpenID4VCI `c_nonce` from the Issuer's <data-elements:Nonce> Endpoint and that the KA carries the same value in its `nonce` claim.
4. Generate as many credentials as there are attested public keys in the KA, where the applicable profile requires multi-key issuance.
5. Bind each issued credential to one of the attested public keys.
6. Ensure that no two issued credentials in the transaction are bound to the same public key.

### **7.5.2 Credential Request using `proofs.attestation`**

Wallets **SHALL**:

1. Include exactly one element in the `attestation` array.
2. Include the OpenID4VCI `c_nonce` obtained from the Issuer's <data-elements:Nonce> Endpoint in the KA's `nonce` claim.
3. Carry the Key Attestation (KA) directly as the single attestation element.

Issuers **SHALL**:

1. Verify that the KA signature validates under the <roles:Wallet Provider (WP)> public key from the applicable trusted list and that its `nonce` claim contains the current OpenID4VCI `c_nonce`.
2. Generate as many credentials as there are attested public keys in the KA, where the applicable profile requires multi-key issuance.
3. Bind each issued credential to one of the attested public keys.
4. Ensure that no two issued credentials in the transaction are bound to the same public key.

Issuers **SHOULD**:

1. Reject malformed or semantically inconsistent `proofs` structures with explicit error information where possible.
2. Distinguish clearly between `c_nonce` failure, DPoP-Nonce failure, attestation failure, proof failure, and policy failure.

### **7.6 Deferred Credential Endpoint**

Issuers **SHALL**:

1. Expose a Deferred Credential Endpoint where the deployment supports deferred issuance.
2. Return the information needed by the Wallet to retrieve deferred credentials.
3. Validate deferred retrieval tokens, references, or transaction identifiers.
4. Publish the Deferred Credential Endpoint in metadata where supported.
5. Return explicit terminal errors for expired, denied, or otherwise failed deferred issuance transactions.

Issuers **SHOULD**:

1. Provide retry guidance or polling hints.
2. Preserve transaction state for a duration appropriate to the issuance process.

Wallets **SHALL**:

1. Recognise deferred issuance responses.
2. Persist the transaction state needed to continue deferred retrieval.
3. Poll or retry according to the Issuer's guidance until completion or terminal failure.
4. Distinguish pending and failed issuance states in Wallet behaviour.
5. Use `Authorization: DPoP {access_token}` and a DPoP proof bound to the access-token key for deferred retrieval.

Wallets **SHOULD**:

1. Apply retry intervals and back-off.
2. Allow the <roles:User> to stop retrying or resume later.

### **7.7 Server Metadata**

Issuers **SHALL** publish metadata that includes:

1. OAuth 2.0 / OpenID configuration, including Authorisation, Token, and PAR endpoints.
2. <roles:Attestation Provider (AP)|Attestation Provider> metadata describing supported credential configurations.
3. The Credential Endpoint location.
4. The Deferred Credential Endpoint location, where supported.
5. Any relevant proof types, credential format support, and associated configuration data required by Wallets.
6. The format identifiers for SD-JWT VC and ISO mdoc.
7. Signed Issuer Metadata whose JWS protected header carries the Issuer access certificate (<artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>) in `x5c`.
8. The `issuer_info` metadata parameter is an array of objects carrying issuer registration material, including the registration certificate (distributed as the value of the `issuer_info[].data` parameter whose `issuer_info[].fromat == registration_cert` and profiled as specified in <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>) and registrar dataset, as profiled by ETSI.
9. Authorization Server Metadata advertising DPoP and combined WIA authentication, including at minimum:
   - `token_endpoint_auth_methods_supported` containing `attest_jwt_client_auth_dpop`;
   - `dpop_signing_alg_values_supported`;
   - `client_attestation_pop_methods_supported` containing `dpop_combined`;
   - `client_attestation_signing_alg_values_supported`.

Wallets **SHALL**:

1. Retrieve and process Issuer metadata.
2. Use metadata to construct authorisation and credential requests.
3. Use metadata to interpret <artifacts:Credential Offer|Credential Offers> and supported credential configurations.
4. Where notification support is implemented and the Issuer provides a `notification_id`, use Issuer metadata or the applicable profile to determine how Notification Requests are sent.
5. Process signed Issuer Metadata `x5c` (WRPAC) and `issuer_info` (WRPRC) content as part of issuer validation and registration-material handling.

Issuers that support Interactive Authorization publish the metadata in Section 7.8. Wallets that do not support Interactive Authorization ignore `authorization_challenge_endpoint` and `require_interactive_authorization`.

### **7.8 Interactive Authorization**

Support for Interactive Authorization is OPTIONAL for Issuers and for Wallets. An Issuer that does not support it, and a Wallet that does not implement it, remain conformant. This section applies where it is supported.

Interactive Authorization lets the Issuer qualify the Holder before issuing, with the authorisation request carried on the back channel. The Wallet declares which interaction types it supports. The <components:Authorization Server|Authorisation Server> either returns an authorisation code or names the one interaction it requires. A credential presentation in that exchange is still a presentation: the <roles:User> decides what is disclosed. The same exchange can serve a Wallet that has a user interface and a Wallet acting without a browser, including machine-to-machine issuance, because the final step stays on the back channel when the presentation interaction is used.

Interactive Authorization replaces PAR for that transaction. The requirements of Section 7.3 do not apply to the exchange. The Token Endpoint requirements of Section 7.4 apply to the resulting authorisation code, including <artifacts:Wallet Instance Attestation (WIA)|WIA> client authentication, DPoP, and <protocols:PKCE>.

The interaction type this RFC specifies for interoperability is `urn:openid:dcp:ia:openid4vp_presentation`. Support for `urn:openid:dcp:ia:auth_via_web` is OPTIONAL even for an implementation that supports Interactive Authorization. Custom interaction types are out of scope. An Issuer SHALL NOT require an interaction type that this RFC does not define.

OpenID4VCI 1.1 says that, for the requested presentation, the Issuer is acting towards the Wallet in the Verifier role, and that the deployment of that function is out of scope of OpenID4VCI. This RFC follows that split. Holder consent, selective disclosure, and the format-specific presentation binding below apply. The following RFC-02 obligations do not apply, because the mechanism they attach to is absent: custom-scheme invocation, the `x509_hash` client identifier scheme, and submission to a Presentation Response Endpoint. Whether `verifier_info` and Relying Party registration apply when an Issuer requests a presentation under Interactive Authorization is unresolved. OpenID4VCI 1.1 does not require `verifier_info` on this request, and this RFC does not add that requirement. Requiring it would mean an Issuer cannot use Interactive Authorization unless it is also registered as a <roles:Relying Party (RP)|Relying Party>. The Issuer's own `issuer_info` and <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC> obligations in this RFC are unchanged.

Issuers that support Interactive Authorization **SHALL**:

1. Expose an Authorization Challenge Endpoint and publish it as `authorization_challenge_endpoint` in Authorization Server Metadata. Its presence is how a Wallet learns that Interactive Authorization is available.
2. Accept the Authorization Challenge Request parameters defined by OAuth 2.0 for First-Party Applications, plus `interaction_types_supported` as defined by OpenID4VCI 1.1.
3. Require, on every Authorization Challenge Request, the same combined <artifacts:Wallet Instance Attestation (WIA)|WIA> and DPoP client authentication this RFC requires at PAR: `OAuth-Client-Attestation` carrying the <artifacts:Wallet Instance Attestation (WIA)|WIA>, and a `DPoP` proof signed by the key in the <artifacts:Wallet Instance Attestation (WIA)|WIA> `cnf` claim. Apply the validation rules in Section 7.3, items 9 to 12, including `use_dpop_nonce` when the proof does not carry a current nonce.
4. Require `code_challenge` and `code_challenge_method=S256` on the initial Authorization Challenge Request.
5. Where the request cannot yet be authorised, respond with HTTP 403 and error `insufficient_authorization`, and set `interaction_type_required` to exactly one interaction type the Wallet listed. Where the Issuer needs an interaction type the Wallet did not list, return `missing_interaction_type` and do not continue.
6. Generate a fresh `auth_session` on every challenge response that uses it, with at least 256 bits of entropy, distinct from every previous value, and opaque to the Wallet.
7. Bind `auth_session` to the DPoP public key of the <artifacts:Wallet Instance Attestation (WIA)|WIA>. Verify the DPoP proof on every request that carries an `auth_session`, and reject a request that presents a different key.
8. For `urn:openid:dcp:ia:openid4vp_presentation`, include `auth_session` and an `openid4vp_request`. Set `response_mode` to `ia_post` or `ia_post.jwt`. Do not use `dc_api` or `dc_api.jwt`: those response modes return the response through the browser, and this exchange has no browser.
9. For that interaction type, bind the OpenID4VP `nonce` to the `auth_session` and verify that the presentation used that nonce.
10. For that interaction type, require the presentation to be bound to this <components:Authorization Server|Authorisation Server>'s Authorization Challenge Endpoint, using the Credential Format rules in Section 7.8.1. Reject a presentation that is not bound to that endpoint.
11. Where `expected_origins` is included in the presentation request, set it to only the derived Origin of this Authorization Challenge Endpoint (the origin of `https://as.example.com/challenge` is `https://as.example.com`).
12. For `urn:openid:dcp:ia:auth_via_web`, omit `auth_session` from the challenge response, return a `request_uri`, and treat that `request_uri` as single-use. Where the initial request used <protocols:PKCE>, enforce `code_verifier` on the intermediate request that follows the browser step.
13. Where the Issuer prepared the issuance for a Holder it had already authenticated, accept `issuer_state` on the initial Authorization Challenge Request only, treat it as single-use, and refuse the exchange unless the presented credential identifies that Holder. Reject a request that carries `issuer_state` together with `auth_session`. The format bindings in Section 7.8.1 bind a presentation to the <components:Authorization Server|Authorisation Server>, so the Holder check is separate and is the Issuer's responsibility.
14. Publish `require_interactive_authorization` only together with `authorization_challenge_endpoint`, and only for a deployment that is limited to Wallets implementing Interactive Authorization. Do not set it on a deployment that must still accept Wallets conforming only to the OpenID4VCI 1.0 baseline of this RFC.

Wallets that support Interactive Authorization **SHALL**:

1. Implement `urn:openid:dcp:ia:openid4vp_presentation`, and list in `interaction_types_supported` every interaction type the Wallet can complete.
2. Send `code_challenge` and `code_challenge_method=S256` on the initial Authorization Challenge Request, and send `code_verifier` when redeeming the resulting authorisation code.
3. Include <artifacts:Wallet Instance Attestation (WIA)|WIA> and a DPoP proof on every Authorization Challenge Request, using the combined mode in Section 5. When the endpoint returns `use_dpop_nonce` with a `DPoP-Nonce` HTTP header, place that nonce in a new DPoP proof and repeat the request.
4. Echo the most recently received `auth_session` on every subsequent request in the exchange. Ignore `auth_session` on a response for an interaction type that does not use it.
5. Abort the issuance if `interaction_type_required` is a type the Wallet did not list or does not implement.
6. For `urn:openid:dcp:ia:openid4vp_presentation`, process `openid4vp_request` as an OpenID4VP authorization request in Digital Credentials API request shape, obtain <roles:User> consent, and disclose only the claims the <roles:User> authorises.
7. For that interaction type, where `expected_origins` is present, refuse the request unless it contains only the derived Origin of the Authorization Challenge Endpoint the Wallet called.
8. For that interaction type, bind the presentation to that Authorization Challenge Endpoint as specified in Section 7.8.1, and return it to the same endpoint in `openid4vp_response`, together with the current `auth_session`.
9. Support response modes `ia_post` and `ia_post.jwt`. Where `ia_post.jwt` is used, encrypt the response with `A128GCM` or `A256GCM`.
10. For `urn:openid:dcp:ia:auth_via_web`, open `request_uri` in an external user agent. The `redirect_uri` used with that interaction SHALL be an `https` URL. The Wallet SHALL NOT use an embedded user agent. Use a returned `request_uri` only once. Where the Wallet has more than one issuance session in progress, include `state` so the redirect can be matched to the session.
11. Where a <artifacts:Credential Offer> uses the `authorization_code` grant and carries `issuer_state`, and the Wallet continues that offer with Interactive Authorization, include `issuer_state` on the initial Authorization Challenge Request only. Do not send `issuer_state` on a request that carries `auth_session`.

#### **7.8.1 Provisional readings of the editor's draft**

OpenID4VCI 1.1 is an editor's draft. The readings below are what this RFC tests against. Implementations SHOULD keep the affected identifiers configurable. If the published specification differs, the published text prevails and this RFC is revised.

The draft's change log records a rename to the prefix `iae:`, the response mode `iae_post`, and the metadata parameters `interactive_authorization_endpoint` and `require_interactive_authorization_request`. The normative text uses `ia:`, `ia_post` and `ia_post.jwt`, `authorization_challenge_endpoint`, and `require_interactive_authorization`. The ISO mdoc section names its handover `OpenID4VCIIAEHandover`, so the `IAE` spelling also appears inside the normative text. This RFC follows the normative text, and uses the mdoc handover label as written. This discrepancy is recorded as [OpenID4VCI issue 811](https://github.com/openid/OpenID4VCI/issues/811).

For an SD-JWT VC presentation, the Key Binding JWT `aud` claim SHALL be the derived Origin of the Authorization Challenge Endpoint, prefixed with `ia:`. For the endpoint `https://as.example.com/challenge`, that value is `ia:https://as.example.com`. The draft's normative sentence says derived Origin. An example in the same section shows the full endpoint URL. This RFC follows the normative sentence. This discrepancy is recorded as [OpenID4VCI issue 812](https://github.com/openid/OpenID4VCI/issues/812).

For an ISO mdoc presentation, the Wallet SHALL use the `SessionTranscript` defined for Interactive Authorization in OpenID4VCI 1.1. `DeviceEngagementBytes` and `EReaderKeyBytes` are `null`. The handover type string is `OpenID4VCIIAEHandover`. The first element of the handover info is the Authorization Challenge Endpoint URL with no `ia:` prefix. The handover hash SHALL be the SHA-256 hash of the bare CBOR encoding of that handover info. The draft's CDDL describes the hash input as the byte string that wraps the encoded structure, and the prose and the worked example hash the encoding without that wrapper. Those two inputs differ by the byte-string header. This RFC follows the prose and the worked example. This discrepancy is recorded as [OpenID4VCI issue 814](https://github.com/openid/OpenID4VCI/issues/814).

Interactive Authorization in the draft is Wallet-initiated. `issuer_state` is not one of the Authorization Challenge Request parameters. Section 5.1 of OAuth 2.0 for First-Party Applications permits extension parameters, so this RFC accepts `issuer_state` with the meaning OpenID4VCI 1.0 already gives it on the `authorization_code` grant of a <artifacts:Credential Offer>. The gap is recorded as [OpenID4VCI issue 815](https://github.com/openid/OpenID4VCI/issues/815).

## **8 Interface Definitions**

This section defines the logical interfaces for conformance testing. Exact URL paths are deployment-specific and discovered through metadata.

### **8.1 Wallet Invocation Interface**

- **Direction**: Issuer to Wallet  
- **Transport**: custom URI, QR code, or equivalent Wallet invocation mechanism

Wallets and Issuers **SHOULD** support at least one interoperable Wallet invocation method suitable for both same-device and cross-device use.

For same-device invocation, Wallets and Issuers **SHALL** support the custom URL schemes `openid-credential-offer://` (OpenID4VCI), `haip-vci://` (HAIP), and `eu-eaa-offer://` (ETSI).

### **8.2 Credential Offer Interface**

- **Direction**: Issuer to Wallet

The <artifacts:Credential Offer> **SHALL** contain at least:

- `credential_issuer`;  
- grant information;  
- credential identifiers or credential configuration identifiers;  
- the information the Wallet needs to continue the issuance flow.

The exact JSON structure SHALL comply with OpenID4VCI.

### **8.3 PAR Endpoint**

- **Direction**: Wallet to Issuer (AS)  
- **Method**: `POST`

#### **Request (logical fields)**

- `client_id`  
- credential-related authorisation parameters  
- `code_challenge`  
- `code_challenge_method=S256`  
- `redirect_uri`  
- `response_type=code`  
- `state`  
- WIA client authentication and DPoP proof

#### **Response**

- `request_uri`  
- `expires_in`
- `DPoP-Nonce` HTTP response header on a `use_dpop_nonce` error when the proof did not carry a fresh nonce, and when the AS issues a nonce for the next request

### **8.4 Token Endpoint**

- **Direction**: Wallet to Issuer (AS)  
- **Method**: `POST`

#### **Request (logical fields)**

- `grant_type=authorization_code` or `grant_type=urn:ietf:params:oauth:grant-type:pre-authorized_code`
- `code`, `redirect_uri`, and `code_verifier` for Authorization Code Flow
- `pre-authorized_code` and any required transaction code for Pre-Authorized Code Flow
- `OAuth-Client-Attestation: <WIA>`
- `DPoP: <proof>`

#### **Response**

- `access_token` whose confirmation member contains `cnf.jkt`
- `token_type=DPoP`
- `expires_in`  
- optional `refresh_token` or other explicitly defined OAuth/OpenID4VCI parameters
- `DPoP-Nonce` HTTP response header on a `use_dpop_nonce` error when the proof did not carry a fresh nonce, and when the AS issues a nonce for the next request

### **8.5 Credential Endpoint**

- **Direction**: Wallet to Issuer  
- **Method**: `POST`

#### **Request (logical fields)**

- `Authorization: DPoP {access_token}`
- requested credential configuration or identifier  
- format-specific request information  
- proof material, including KA where device binding is used
- `DPoP: <proof>`

#### **Response**

- issued credential(s), or  
- deferred issuance response
- `DPoP-Nonce` HTTP header on a `use_dpop_nonce` error

### **8.6 Nonce Endpoint**

- **Direction**: Wallet to Issuer  
- **Method**: `POST` or as defined by metadata/profile

The Nonce Endpoint returns OpenID4VCI `c_nonce` in its JSON response body. The Wallet obtains `c_nonce` immediately before generating Credential Endpoint proof material or KA. The Resource Server SHALL return a `DPoP-Nonce` HTTP response header on that response. If the request does not present a fresh DPoP nonce, the Resource Server SHALL reject it with error code `use_dpop_nonce` and a `DPoP-Nonce` HTTP header. The Wallet SHALL place that nonce in the `nonce` claim of the DPoP proof. `DPoP-Nonce` and `c_nonce` are separate values and mechanisms.

### **8.7 Notification Interface**

- **Direction**: Wallet to Issuer  
- **Method**: `POST` or as defined by metadata/profile

If the deployment supports issuance notifications and the Issuer provides a `notification_id`, the Wallet **SHOULD** send one or more Notification Requests for that `notification_id` using the mechanism defined by the applicable profile or Issuer metadata.

### **8.8 Deferred Credential Endpoint**

- **Direction**: Wallet to Issuer  
- **Method**: `POST`

#### **Request (logical fields)**

- `Authorization: DPoP {access_token}`
- `DPoP: <proof>` bound to the access-token key
- transaction identifier, where applicable

#### **Response**

- issued credential(s), or  
- pending status with retry guidance, or  
- terminal failure

### **8.9 Metadata Endpoints**

Issuers **SHALL** publish Credential Issuer Metadata and Authorization Server Metadata as separate discovery documents. The Wallet retrieves them separately, following the selection rules in Section 6.1.1.

**Credential Issuer metadata** is published at the Credential Issuer metadata endpoint (`<Credential Issuer identifier>/.well-known/openid-credential-issuer`). It **SHALL** provide:

- <roles:Attestation Provider (AP)|Attestation Provider> metadata;
- supported credential configurations and the request parameters needed to initiate issuance;
- supported grant types;
- supported proof types and formats, including the format identifiers for SD-JWT VC and ISO mdoc;
- the Credential Endpoint location;
- the Deferred Credential Endpoint location, where supported;
- the <data-elements:Nonce> Endpoint location;
- the Authorization Server issuer identifier, using `authorization_servers` when present or the Credential Issuer identifier otherwise;
- signed Issuer Metadata whose JWS protected header carries the Issuer access certificate (<artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>) in `x5c`;
- the `issuer_info` metadata parameter carrying issuer registration material (<artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>), including the registration certificate and registrar dataset, as profiled by ETSI.

Signed Issuer Metadata MAY also carry an optional embedded disclosure policy. Where the Issuer includes one, the Wallet stores and processes that policy as defined by the APTITUDE Trust Framework and RFC-03.

Example, abridged and unsigned:

```json
{
  "credential_issuer": "https://issuer.example.com",
  "authorization_servers": ["https://as.example.com"],
  "nonce_endpoint": "https://issuer.example.com/nonce",
  "credential_endpoint": "https://issuer.example.com/credential",
  "deferred_credential_endpoint": "https://issuer.example.com/deferred",
  "credential_configurations_supported": {},
  "issuer_info": [
    {...},
    {...}
  ]
}
```

When metadata is signed, the JWS protected header carries `x5c` with the <artifacts:Wallet-Relying Party Access Certificate (WRPAC)|WRPAC>, and the payload includes `issuer_info` for the <artifacts:Wallet-Relying Party Registration Certificate (WRPRC)|WRPRC>.

**Authorization Server metadata** is published at the Authorization Server metadata endpoint defined by RFC 8414. It **SHALL** provide:

- authorisation endpoint;
- token endpoint;
- PAR endpoint;
- `token_endpoint_auth_methods_supported` containing `attest_jwt_client_auth_dpop`;
- `dpop_signing_alg_values_supported`;
- `client_attestation_pop_methods_supported` containing `dpop_combined`;
- `client_attestation_signing_alg_values_supported`.

`client_attestation_signing_alg_values_supported` lists the JWS algorithms the <components:Authorization Server|Authorisation Server> accepts for the <artifacts:Wallet Instance Attestation (WIA)|WIA>.

Example, abridged:

```json
{
  "issuer": "https://as.example.com",
  "authorization_endpoint": "https://as.example.com/authorize",
  "token_endpoint": "https://as.example.com/token",
  "pushed_authorization_request_endpoint": "https://as.example.com/par",
  "token_endpoint_auth_methods_supported": ["attest_jwt_client_auth_dpop"],
  "dpop_signing_alg_values_supported": ["ES256"],
  "client_attestation_pop_methods_supported": ["dpop_combined"],
  "client_attestation_signing_alg_values_supported": ["ES256"]
}
```

Where the <components:Authorization Server|Authorisation Server> supports Interactive Authorization, Authorization Server Metadata also contains `authorization_challenge_endpoint`. It contains `require_interactive_authorization` only under the condition in Section 7.8.

### **8.10 Authorization Challenge Endpoint**

This interface applies only where Interactive Authorization is supported.

- **Direction**: Wallet to Issuer (AS)
- **Method**: `POST`
- **Content type**: `application/x-www-form-urlencoded`

#### **Initial request (logical fields)**

- credential-related authorisation parameters, including `authorization_details` or `scope` as required for the selected credential configuration
- `response_type=code`
- `client_id`
- `code_challenge` and `code_challenge_method=S256`
- `interaction_types_supported`, including `urn:openid:dcp:ia:openid4vp_presentation`
- `issuer_state`, where the Wallet is redeeming an issuer-initiated `authorization_code` grant that carries one
- `redirect_uri`, where `urn:openid:dcp:ia:auth_via_web` is listed; the value is an `https` URL
- `OAuth-Client-Attestation: <WIA>`
- `DPoP: <proof>`

#### **Interaction-required response**

HTTP 403, `Content-Type: application/json`, error `insufficient_authorization`, and exactly one `interaction_type_required`.

For `urn:openid:dcp:ia:openid4vp_presentation`:

- `auth_session`
- `openid4vp_request`, with `response_mode` of `ia_post` or `ia_post.jwt`

For `urn:openid:dcp:ia:auth_via_web`:

- `request_uri`
- optional `expires_in`
- no `auth_session`

#### **Presentation follow-up (logical fields)**

- `auth_session`
- `openid4vp_response`
- `OAuth-Client-Attestation: <WIA>`
- `DPoP: <proof>` signed by the same key as the initial request

#### **Successful response**

- authorisation `code`, as a JSON object
- the Wallet redeems that code at the Token Endpoint (Section 8.4)

#### **Error codes used by this profile**

- `insufficient_authorization`: a further interaction is required
- `missing_interaction_type`: the Wallet did not list an interaction type the Issuer requires
- `use_dpop_nonce`: the DPoP proof did not carry a current nonce; the response includes a `DPoP-Nonce` HTTP header

## **9 Conformance**

An implementation **conforms to this specification as a Wallet** if it:

1. Implements the Wallet requirements in Sections 6 and 7
2. Supports the Wallet-side interfaces and behaviours defined in Section 8
3. Uses OpenID4VCI 1.0 and the APTITUDE issuance profile constraints defined in this RFC.

Support for Interactive Authorization (Sections 6.4, 7.8, and 8.10) is OPTIONAL. A Wallet or Issuer that does not implement it still conforms. A Wallet or Issuer that claims support implements those sections. `require_interactive_authorization` set to `true` is not a baseline deployment of this RFC.

An implementation **conforms to this specification as an Issuer** if it:

1. Implements the Issuer requirements in Sections 6 and 7
2. Publishes the required metadata.
3. Provides the issuance interfaces defined in Section 8
4. Applies the APTITUDE issuance baseline consistently across supported credential configurations.

Pilot-specific profiles MAY define additional constraints for specific credential types or domains. Such profiles SHALL NOT relax the mandatory requirements in this document.

9.1 Scope of the Conformance Matrix

This conformance matrix verifies baseline protocol interoperability between an Issuer or <components:Wallet Unit> under test and the reference issuance endpoints defined by this APTITUDE Issuance Profile. It is intended to confirm correct support for representative OpenID4VCI v1.0 issuance flows covered by this RFC, including wallet-initiated and issuer-initiated issuance.

The matrix is a protocol interoperability matrix, not a complete ARF v3.0.0 or CIR 2024/2982 / CIR 2024/2979 / CIR 2024/2977 compliance assessment. It focuses on issuance flow processing, <artifacts:Credential Offer> handling, PAR-based authorisation, token acquisition, proof-bound credential requests, deferred issuance handling, and metadata-driven endpoint use within the scope of this profile. Interactive Authorization is outside the baseline matrix. `VCI-CHECK-12` and `VCI-011` apply only when the Wallet under test and the reference Issuer both claim support for it.

It does not exhaustively test broader trust, governance, semantic, privacy, supervisory, or deployment-specific obligations. Where ARF v3.0.0 or CIR identifiers are included, they provide traceability and alignment for the issuance interoperability capability being exercised, rather than full normative coverage of the broader requirement domain. This is consistent with the RFC’s explicitly horizontal, cross-pilot scope and its stated out-of-scope exclusions.
