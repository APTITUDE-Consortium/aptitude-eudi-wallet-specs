# RB05 v0.1 — Conformance and pilot test catalogue

**Status:** Draft proposal v0.1 — for discussion, not approved\
**Author:** Hedi Hidouri, IN Groupe\
**Alignment revision:** 8 September 2026\
**Editorial revision:** 11 September 2026 — review-package links and wording; test scenarios unchanged\
**Test-data rule:** every vector embedded in or shared with this package SHALL use synthetic identities and synthetic/non-biometric payload bytes. Schema, parser and complete-protocol correlation tests SHALL use synthetic data. A controlled evaluation whose purpose inherently requires biometric material—such as matcher/PAD performance, inversion/reconstruction resistance or template-level linkability—may use only an approved, lawful and representative controlled corpus after all gates applicable to that test are closed, including D05, D06, D13, D15, D16 and D17 as relevant. No biometric sample or template may be embedded in shared artefacts or reports; only approved aggregate, privacy-safe evidence may leave the controlled environment. D18 also applies when a travel credential is combined.

Decision identifiers refer to the production approval gates in the [RB05 Rulebook](RB05_BIOMETRIC_PROFILE_RULEBOOK_v0.1.md).

## Test result model

Each execution record should contain: test ID, implementation/version, environment, date, synthetic input-vector ID, expected outcome, actual outcome, pass/fail, privacy-safe evidence link and reviewer. It SHALL NOT contain a portrait, live sample, template bytes, biometric score, full mdoc, holder name, RB05 `document_number`, source-document number or another persistent holder/credential identifier.

Each record must also identify its selected route and applicability. **R1** is D4.1's Biometric Profile to Ready-to-Travel association and subsequent Ready-to-Travel/QR checkpoint flow; **R2** is the proposed direct-RB05 checkpoint flow with independently validated travel-entitlement evidence. Section A validates RB05's candidate namespace model, never Ready-to-Travel. Section B tests RB05 issuance. Sections C–E describe the candidate direct-RB05 controls; any use of those controls during R1 association and the separate R1 checkpoint must be mapped in the D12/D18 specification. Section F includes route-selection and integration tests. An unselected-route test is recorded as not applicable with its decision reference, never as passed. A planned test is not evidence that its flow is implemented.

## Minimum evidence before real-person pilot

The pilot gate requires the RB05 schema/issuance tests and all presentation/integration tests applicable to each selected route, the negative category and one-to-many tests, independent biometric/PAD evidence, retention inspection, DPIA/legal approval, accessible fallback and a privacy review of test evidence. R1 additionally requires its own approved Ready-to-Travel/QR conformance tests; the RB05 catalogue alone does not supply that complete profile. Unselected-route cases require a justified not-applicable record. A passing happy path alone is not sufficient.

This document is a catalogue, not an execution report. It specifies planned acceptance tests and does not claim that they have been executed. Passing local schema or example checks does not demonstrate signed-mdoc, Wallet, reader, biometric or end-to-end interoperability. Those tests require the relevant decisions, implementation components and test evidence.
